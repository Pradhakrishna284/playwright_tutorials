SECTION 1: ARCHITECTURE OVERVIEW
================================================================================

WHAT IS PLAYWRIGHT ARCHITECTURE?

Playwright is a sophisticated test automation framework with multiple layers
of abstraction and components working in concert.

HIGH-LEVEL VIEW:

    ┌──────────────────────────────────────────────────────────────┐

SECTION 1.1: CLIENT-SERVER-BROWSER ARCHITECTURE (DETAILED)
================================================================================

PLAYWRIGHT FOLLOWS A CLIENT-SERVER-BROWSER PATTERN:

THREE-TIER ARCHITECTURE:

Tier 1: CLIENT (Your Test Code)
───────────────────────────────
    Location: Your machine, Node.js process
    Runs: Your test file (pw_xpath.spec.ts)
    Writes: High-level Playwright API calls
    
    Example:
        const link = page.locator('//a[@class="product"]');
        await link.click();
    
    Characteristics:
        ├─ Simple, readable syntax
        ├─ No direct browser access
        ├─ Communicates via WebSocket
        ├─ Waits for server responses
        └─ Unaware of protocol details


Tier 2: SERVER (Playwright Automation Server)
───────────────────────────────────────────────
    Location: Same machine, or remote (headless cloud)
    Function: Bridge between client and browser
    Communicates: Via WebSocket connection
    
    Responsibilities:
        ├─ Receive API calls from client
        ├─ Convert to CDP protocol messages
        ├─ Send commands to browser
        ├─ Receive events from browser
        ├─ Convert responses back to JavaScript
        ├─ Handle retries and timeouts
        └─ Manage browser lifecycle
    
    Not visible in your code - you never interact directly with it


Tier 3: BROWSER (Actual Browser Process)
──────────────────────────────────────────
    Location: Separate system process
    Executable: chrome.exe, firefox.exe, playwright-webkit, etc.
    Function: Execute automation commands
    
    Capabilities:
        ├─ Parse HTML/CSS/JavaScript
        ├─ Render pages
        ├─ Execute JavaScript
        ├─ Simulate user input
        ├─ Network requests
        └─ Send back results


ARCHITECTURE DIAGRAM (Detailed):

    ┌────────────────────────────────────────────────────────────┐
    │ YOUR MACHINE / YOUR ENVIRONMENT                            │
    │                                                             │

    └────────────────────────────────────────────────────────────┘


COMMUNICATION FLOW EXAMPLE:

Step 1: Client Code Execution
    test code → await page.click('#button')
    
Step 2: Client Prepares
    - Parse selector '#button'
    - Create Locator object
    - Prepare click action
    
Step 3: Client → Server Communication
    Send over WebSocket:
    {
      "id": 42,
      "method": "DOM.querySelector",
      "params": { "selector": "#button" }
    }
    
Step 4: Server Processing
    - Receive JSON message
    - Validate protocol
    - Create CDP command
    - Forward to browser
    
Step 5: Server → Browser Communication
    Send CDP protocol message:
    {
      "id": 42,
      "method": "Input.dispatchMouseEvent",
      "params": { "type": "mousePressed", "x": 100, "y": 50 }
    }
    
Step 6: Browser Execution
    - Parse CDP message
    - Find element (#button)
    - Simulate mouse press at coordinates
    - Trigger click event
    - Execute onclick handlers
    
Step 7: Browser → Server Communication
    Send response:
    {
      "id": 42,
      "result": {}
    }
    
Step 8: Server → Client Communication
    Forward response over WebSocket
    JavaScript promise resolves
    
Step 9: Test Code Continues
    Next line in test executes
    console.log('Button clicked')


KEY SEPARATION PRINCIPLE:

┌─────────────────────────────────────────────────────┐
│ CLIENT (Your Code)      │ What you see              │
│                         │ ├─ Simple API             │
│                         │ ├─ Clean syntax           │
│                         │ └─ Readable test code     │
├─────────────────────────────────────────────────────┤
│ SERVER (Playwright)     │ What you don't see        │
│                         │ ├─ Protocol details       │
│                         │ ├─ Network handling       │
│                         │ ├─ Error recovery         │
│                         │ └─ Optimization           │
├─────────────────────────────────────────────────────┤
│ BROWSER (Engine)        │ What actually executes    │
│                         │ ├─ DOM manipulation       │
│                         │ ├─ JavaScript execution   │
│                         │ ├─ Network requests       │
│                         │ └─ Rendering              │
└─────────────────────────────────────────────────────┘


BENEFITS OF THIS ARCHITECTURE:

1. ABSTRACTION
   └─ Users write simple code, complexity hidden in server

2. CROSS-BROWSER SUPPORT
   └─ Same client code, different browser processes
   └─ Server abstracts browser-specific details

3. REMOTE EXECUTION
   └─ Browser can run on different machine
   └─ Server bridges the gap via WebSocket

4. SCALABILITY
   └─ Multiple clients can control multiple browsers
   └─ Server manages connections and state

5. MAINTAINABILITY
   └─ Clear separation of concerns
   └─ Changes to protocol don't affect client code

6. RELIABILITY
   └─ Server can retry failed operations
   └─ Network issues handled transparently
   └─ Timeout management at server level

SECTION 2: CORE COMPONENTS
================================================================================

COMPONENT 1: TEST RUNNER
───────────────────────

Responsibility: Orchestrate test execution

Sub-components:
  ├─ CLI Parser
  │  └─ Parses command-line arguments
  │     Example: npx playwright test pw_xpath.spec.ts
  │
  ├─ Config Loader
  │  └─ Loads and validates playwright.config.ts
  │     ├─ testDir: './tests'
  │     ├─ workers: undefined (auto-detect)
  │     ├─ timeout: 30000
  │     └─ baseURL: 'https://demo.nopcommerce.com'
  │
  ├─ Test Discovery Engine
  │  └─ Scans directories, finds and parses test files
  │     ├─ File pattern: **/*.spec.ts
  │     ├─ Excludes: **/example.spec.ts
  │     └─ Builds test registry
  │
  ├─ Worker Manager
  │  └─ Creates and manages worker processes
  │     ├─ Spawns: 6 workers (auto-detected)
  │     ├─ Manages: Worker pool
  │     ├─ Distributes: Tests to workers
  │     └─ Collects: Results from workers
  │
  ├─ Reporter System
  │  └─ Generates test reports
  │     ├─ Console output
  │     ├─ HTML report
  │     ├─ JSON results
  │     └─ Timing data
  │
  └─ Result Aggregator
     └─ Combines results from all workers
        ├─ Pass/Fail summary
        ├─ Timing statistics
        └─ Exit code determination


COMPONENT 2: API LAYER
──────────────────────

Responsibility: Provide user-facing test API

Sub-components:
  ├─ Browser API
  │  └─ Launch and manage browser instances
  │     const browser = await playwright.chromium.launch();
  │
  ├─ Context API
  │  └─ Create isolated browser contexts
  │     const context = await browser.newContext();
  │
  ├─ Page API
  │  └─ Interact with web pages
  │     const page = await context.newPage();
  │     await page.goto('https://demowebshop.tricentis.com/');
  │
  ├─ Locator API
  │  └─ Find and interact with elements
  │     const link = page.locator('//a[@class="product"]');
  │     await link.click();
  │
  ├─ Network API
  │  └─ Intercept and modify network requests
  │     await page.route('**/*.css', route => route.abort());
  │
  ├─ Keyboard API
  │  └─ Send keyboard input
  │     await page.keyboard.press('Enter');
  │
  ├─ Mouse API
  │  └─ Send mouse input
  │     await page.mouse.click(100, 200);
  │
  └─ Assertion API
     └─ Test assertions
        await expect(page.locator('#element')).toBeVisible();


COMPONENT 3: LOCATOR ENGINE
────────────────────────────

Responsibility: Element selection and querying

Sub-components:
  ├─ CSS Selector Engine
  │  └─ Parse and execute CSS selectors
  │     Example: page.locator('.product-link')
  │
  ├─ XPath Engine
  │  └─ Parse and execute XPath expressions
  │     Example: page.locator('//a[@class="product"]')
  │
  ├─ Text Matcher
  │  └─ Find elements by text content
  │     Example: page.locator('text=Products')
  │
  ├─ Role Matcher
  │  └─ Find elements by accessibility role
  │     Example: page.locator('[role="button"]')
  │
  ├─ Test ID Matcher
  │  └─ Find elements by test ID attribute
  │     Example: page.locator('[data-testid="submit"]')
  │
  └─ Composite Locator
     └─ Chain multiple locators
        Example: page.locator('#form').locator('button:first')


COMPONENT 4: BROWSER AUTOMATION
────────────────────────────────

Responsibility: Communicate with browser via protocol

Sub-components:
  ├─ CDP Client (Chrome DevTools Protocol)
  │  └─ WebSocket connection to browser
  │     ├─ Sends commands: page navigation, clicks, etc.
  │     ├─ Receives events: page loaded, element found, etc.
  │     └─ Binary communication format
  │
  ├─ Command Executor
  │  └─ Translates high-level API calls to CDP commands
  │     Input: page.click('#button')
  │     Output: CDP message to browser
  │
  ├─ Event Handler
  │  └─ Processes browser events
  │     ├─ Page lifecycle events
  │     ├─ Navigation events
  │     ├─ Console messages
  │     └─ Network events
  │
  └─ Waiter System
     └─ Wait for conditions
        ├─ Wait for navigation
        ├─ Wait for element
        ├─ Wait for timeout
        └─ Wait for function


COMPONENT 5: FIXTURE SYSTEM
────────────────────────────

Responsibility: Provide reusable test setup/teardown

Sub-components:
  ├─ Built-in Fixtures
  │  ├─ page: Browser page instance
  │  ├─ browser: Browser instance
  │  ├─ browserName: 'chromium' | 'firefox' | 'webkit'
  │  ├─ context: Browser context
  │  └─ request: HTTP API client
  │
  ├─ Custom Fixtures
  │  └─ User-defined setup/teardown
  │     const test = base.extend({
  │       testUser: async ({}, use) => {
  │         // Setup
  │         const user = await createUser();
  │         await use(user);
  │         // Teardown
  │         await deleteUser(user.id);
  │       },
  │     });
  │
  └─ Fixture Dependency Resolver
     └─ Manages fixture dependencies and scoping


COMPONENT 6: PROJECT SYSTEM
────────────────────────────

Responsibility: Run tests across multiple configurations

Sub-components:
  ├─ Project Loader
  │  └─ Load project configurations
  │     Example: chromium, firefox, webkit
  │
  ├─ Device Emulator
  │  └─ Emulate mobile devices
  │     Example: 'Pixel 5', 'iPhone 12'
  │
  └─ Configuration Merger
     └─ Merge project config with global config

┌───────────────────────────────────────────────────────┐

│                                                        │

│ https://demo.nopcommerce.com/                         │

KEY PRINCIPLES:

1. ABSTRACTION
   ├─ High-level API hides protocol complexity
   └─ Users write clean test code

2. SEPARATION OF CONCERNS
   ├─ Each layer has specific responsibility
   └─ Changes don't cascade across layers

3. TESTABILITY
   ├─ Each layer can be tested independently
   └─ Mocking at each boundary is possible

4. PERFORMANCE
   ├─ Protocol optimization at lower layers
   └─ Caching and batching where possible

5. MAINTAINABILITY
   ├─ Clear component boundaries
   └─ Easy to understand data flow

SECTION 4: DATA FLOW THROUGH ARCHITECTURE
================================================================================

EXAMPLE: User clicks a button with page.locator('//a').click()

STEP 1: USER CODE → PUBLIC API
───────────────────────────────

Input code:
    const link = page.locator('//a[@class="product-link"]');
    await link.click();

Processing:
    1. page.locator() is called
       └─ Returns a Locator object (not executed yet)
    
    2. locator.click() is called
       └─ NOW execution begins

Data structure created:
    Locator {
      selector: '//a[@class="product-link"]',
      selectorType: 'xpath',
      timeout: 5000,
      strict: false
    }


STEP 2: PUBLIC API → LOCATOR ENGINE
─────────────────────────────────────

Input: Locator object with XPath selector

Processing in Locator Engine:
    1. Parse XPath expression
       └─ '//a[@class="product-link"]'
    
    2. Create query plan
       └─ XPath engine execution plan
    
    3. Execute in browser context
       └─ JavaScript code to evaluate XPath

Generated JavaScript:
    (function() {
      const evaluator = new XPathEvaluator();
      const result = evaluator.evaluate(
        '//a[@class="product-link"]',
        document,
        null,
        XPathResult.FIRST_ORDERED_NODE_TYPE,
        null
      );
      return result.singleNodeValue;
    })();

Output: Element reference (if found)


STEP 3: LOCATOR ENGINE → PROTOCOL ADAPTATION
───────────────────────────────────────────────

Input: Element reference + action (click)

Processing:
    1. Check if element is visible
       └─ Verify clickable
    
    2. Get element coordinates
       └─ X, Y position
    
    3. Create CDP command
       └─ Input.dispatchMouseEvent

Generated CDP message:
    {
      method: 'Input.dispatchMouseEvent',
      params: {
        type: 'mousePressed',
        x: 342,
        y: 158,
        button: 'left',
        clickCount: 1
      }
    }


STEP 4: PROTOCOL ADAPTATION → COMMUNICATION (WEBSOCKET)
─────────────────────────────────────────────────────────

Input: CDP command object

Processing in Communication Layer:
    1. Serialize CDP command to JSON
    2. Wrap in JSON-RPC envelope with message ID
    3. Create protocol frame
    4. Send over WebSocket connection

WEBSOCKET CONNECTION DETAILS:

Location in Architecture:
    ┌─────────────────────────────────────┐
    │  YOUR TEST CODE (Node.js Process)   │
    │  Running in Terminal/IDE            │
    └────────┬────────────────────────────┘
             │
             │ WebSocket Connection
             │ (ws://localhost:52613/...)
             │
    ┌────────▼────────────────────────────┐
    │  BROWSER PROCESS                    │
    │  (Chromium/Firefox/WebKit)          │
    │  Separate executable process        │
    └─────────────────────────────────────┘

Connection Initialization:
    1. When browser launches, it opens debug port
    2. Playwright connects via WebSocket
    3. Connection stays open throughout test
    4. Closed when browser closes

Example WebSocket URL:
    ws://localhost:52613/devtools/browser/xxxxx

Message Structure (JSON-RPC):
    {
      "id": 42,
      "method": "Input.dispatchMouseEvent",
      "params": {
        "type": "mousePressed",
        "x": 342,
        "y": 158,
        "button": "left",
        "clickCount": 1
      }
    }

Message Flow Over WebSocket:

    Your Code                WebSocket Bridge        Browser
        │                          │                    │
        │  Ready to click         │                    │
        ├─ Create CDP message ───>│                    │
        │  id: 42                 │ Connect if needed  │
        │                         ├─ ws:// connection │

WHY WEBSOCKET FOR BROWSER AUTOMATION:

Without WebSocket (Using HTTP):
    ❌ Request-Response pattern only
    ❌ Browser cannot initiate messages
    ❌ Polling needed for events
    ❌ High latency for real-time control

With WebSocket:
    ✅ Bi-directional communication
    ✅ Browser sends events anytime
    ✅ Instant message delivery
    ✅ Persistent connection
    ✅ Low latency automation
    ✅ Efficient for continuous interaction

1. Command Messages (Test Code → Browser):

CHROME DEVTOOLS PROTOCOL (CDP) ARCHITECTURE:

CDP is the underlying protocol. It's a JSON-RPC protocol over WebSocket.

Message Types:

1. COMMAND (Main Process → Browser)
   Purpose: Instruct browser to do something
   
   Example:
   {
     "id": 1,
     "method": "Page.navigate",
     "params": {
       "url": "https://example.com"
     }
   }

2. RESULT (Browser → Main Process)
   Purpose: Response to command
   
   Example:
   {
     "id": 1,
     "result": {
       "frameId": "ABC123"
     }
   }

3. EVENT (Browser → Main Process)
   Purpose: Browser notifies about something that happened
   
   Example:
   {
     "method": "Page.loadEventFired",
     "params": {
       "timestamp": 1234567890
     }
   }


CDP DOMAINS (Functional areas):

   ├─ Page: Page navigation, lifecycle
   ├─ DOM: DOM access and modification
   ├─ Runtime: JavaScript execution
   ├─ Network: Network interception
   ├─ Input: Keyboard, mouse, touch
   ├─ Debugger: Breakpoints, debugging
   ├─ Profiler: Performance profiling
   ├─ Security: Certificate handling
   ├─ Storage: Cookies, storage
   └─ Target: Tab/context management


COMMAND FLOW EXAMPLE (page.goto):

await page.goto('https://example.com');

1. Playwright receives goto() call
2. Creates CDP command:
   {
     "id": 1,
     "method": "Page.navigate",
     "params": {
       "url": "https://example.com"
     }
   }

3. Sends over WebSocket to browser

4. Browser receives and routes to Page domain

5. Browser initiates HTTP request to example.com

6. Server responds with HTML

7. Browser parses HTML, creates DOM

8. Browser loads subresources (CSS, JS, images)

9. When page is loaded, browser sends event:
   {
     "method": "Page.loadEventFired",
     "params": {...}
   }

10. Playwright receives event

11. Waits for network to settle (no more requests)

12. Promise from goto() resolves

13. User code continues

SECTION 7: API COMMUNICATION PATTERNS
================================================================================

PLAYWRIGHT USES SEVERAL COMMUNICATION PATTERNS:

PATTERN 1: REQUEST-RESPONSE (Synchronous wait)
───────────────────────────────────────────────

await page.goto('https://example.com');

Execution:
    1. Send: Page.navigate command
    2. Wait: For response from browser
    3. Receive: Page.loadEventFired event
    4. Resolve: Promise returns
    5. Continue: Next line executes

Diagram:
    Main Process                    Browser
    ────────────                    ───────
    goto() called
         ↓
    Send: Page.navigate ───────────→ Received
         ↓                           ↓
    Wait for response               Navigate
    (blocked)                       ↓
         ↓                          Send: loadEventFired
    ← ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ Received
    Promise resolves
         ↓
    Continue execution


PATTERN 2: FIRE-AND-FORGET (With callback)
────────────────────────────────────────────

page.on('console', msg => console.log(msg));

Execution:
    1. Register listener
    2. Forget about it
    3. Whenever browser sends console event, callback fires
    4. No blocking

Diagram:
    Main Process                    Browser
    ────────────                    ───────
    page.on('console', callback)
         ↓
    Continue execution immediately
    (listener registered)
         ↓
         ↓                          Browser executes JS
         ↓                          ↓
         ↓                          console.log() called
         ↓                          ↓
         ↓                   Send: Runtime.consoleAPICalled
         ←─ ─ ─ ─ ─ ─ ─ ─ ─ Received
         ↓
    callback() executes


PATTERN 3: BATCH OPERATIONS (Collect and send)
────────────────────────────────────────────────

Optimization: Instead of sending one command per operation,
batch multiple operations and send in one message.

const results = await Promise.all([
  page.locator('#btn1').click(),
  page.locator('#btn2').click(),
  page.locator('#btn3').click()
]);

Execution:
    1. All three click operations prepared
    2. Batched together
    3. Sent to browser in optimized manner
    4. Results collected
    5. All promises resolve


PATTERN 4: EVENT STREAMING (Continuous flow)
──────────────────────────────────────────────

page.on('framenavigated', frame => {
  console.log('Frame navigated:', frame.url);
});

Execution:
    1. Listener registered
    2. Browser sends events continuously
    3. Each event triggers callback
    4. No request-response cycle
    5. Continuous monitoring

PATTERN 1: ABSTRACTION LAYERS
──────────────────────────────

Problem: Browsers have complex protocol (CDP), users need simple API
Solution: Create abstraction layers

User code:     await page.click('#button')
API layer:     page.click() → find element → validate
Locator layer: Resolve selector to element
Protocol layer: Convert to CDP command
Communication:  Send CDP message
Browser:       Execute command

───────────────────────────

Example: Launching browser with options

const browser = await chromium.launch({
  headless: false,
  slowMo: 100,
  devtools: true
});

Creates browser with fluent options, building configuration step-by-step.


PATTERN 3: FIXTURES (DEPENDENCY INJECTION)
────────────────────────────────────────────

test.extend({
  testUser: async ({}, use) => {
    const user = await createUser();
    await use(user);
    await deleteUser(user.id);
  }
});

Provides dependencies to tests, managing setup/teardown.


PATTERN 4: EVENT EMITTER
─────────────────────────

page.on('popup', popup => {
  console.log('New popup:', popup.url());
});

Objects emit events, listeners can react.


PATTERN 5: PROMISE-BASED ASYNC
────────────────────────────────

const result = await page.evaluate('2 + 2');

All async operations return promises, enabling async/await syntax.


PATTERN 6: COMPOSITE PATTERN (Locators)
────────────────────────────────────────

const firstButton = page
  .locator('form')
  .locator('button')
  .first();

Chain locators for complex element selection.


PATTERN 7: COMMAND PATTERN (CDP)
────────────────────────────────

Each API call is converted to a CDP command, which is a specific action
with parameters.

HOW PLAYWRIGHT OPTIMIZES PERFORMANCE:

OPTIMIZATION 1: PARALLEL EXECUTION
──────────────────────────────────

Multiple workers run tests simultaneously:
  ├─ Worker 1: Test 1
  ├─ Worker 2: Test 2
  ├─ Worker 3: Test 3

OPTIMIZATION 2: BATCHING OPERATIONS
────────────────────────────────────

Instead of:
  await page.click('#a');
  await page.click('#b');
  await page.click('#c');
  (3 round trips)

Use:
  await Promise.all([
    page.click('#a'),
    page.click('#b'),
    page.click('#c')
  ]);
  (1 optimized batch)


OPTIMIZATION 3: ELEMENT CACHING
────────────────────────────────

Locators are evaluated lazily and results may be cached:
  const button = page.locator('button');
  await button.click();    // Evaluates selector
  await button.click();    // May use cached reference


OPTIMIZATION 4: NETWORK OPTIMIZATION
─────────────────────────────────────

Can intercept and block unnecessary resources:
  await page.route('**/*.png', route => route.abort());
  (Saves bandwidth, speeds up pages)


OPTIMIZATION 5: HEADLESS MODE
──────────────────────────────

Default: headless: true
  ├─ No GUI overhead
  ├─ Faster execution
  └─ Perfect for CI/CD

Debug: headless: false
  ├─ See browser

  └─ For manual debugging


OPTIMIZATION 6: CONTEXT ISOLATION
──────────────────────────────────

Each worker has own browser context:
  ├─ Isolated cookies
  ├─ Isolated storage
  ├─ Isolated DOM
  └─ No test interference
