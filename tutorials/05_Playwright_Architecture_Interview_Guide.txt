ANSWER FORMULA
================================================================================

STRUCTURE FOR ALL ANSWERS:

1. DEFINE IT (10 seconds)
   └─ What is it in 1-2 sentences?

2. KEY COMPONENTS (30 seconds)
   └─ 3-4 main parts, brief description

3. HOW IT WORKS (60 seconds)
   └─ Flow diagram or step-by-step process

4. WHY IT MATTERS (20 seconds)
   └─ Benefits, performance, or design principle

5. EXAMPLE (Optional, 30 seconds)
   └─ Real scenario or code snippet

Total: 2-3 minutes per answer

Q1: EXPLAIN PLAYWRIGHT ARCHITECTURE
================================================================================

INTERVIEWER: "Describe Playwright's high-level architecture"

ANSWER STRUCTURE:

1. DEFINE IT
────────────
"Playwright is a layered architecture that abstracts browser automation 
through multiple abstraction layers, from user-facing API to low-level 
protocol communication."

2. KEY COMPONENTS
──────────────────
• Test Runner Layer: Manages test discovery, worker pool, execution
• Public API Layer: High-level test APIs (page.goto, page.click)
• Locator Engine: Resolves CSS, XPath, text selectors
• Protocol Layer: Converts API calls to CDP messages
• Browser Automation: Chrome DevTools Protocol (CDP) over WebSocket
• Browser Instance: Actual Chromium/Firefox/WebKit process

3. HOW IT WORKS
────────────────
User code: await page.click('#button')
    ↓
API Layer interprets the call
    ↓
Locator Engine finds the element (CSS/XPath)
    ↓
Protocol Layer creates CDP command
    ↓
Communication Layer sends via WebSocket
    ↓
Browser receives and executes
    ↓
Result sent back, promise resolves
    ↓
User code continues

4. WHY IT MATTERS
──────────────────
✓ Abstraction: Users don't worry about CDP protocol complexity
✓ Separation of Concerns: Each layer has specific responsibility
✓ Multi-browser support: Same API for Chromium, Firefox, WebKit
✓ Performance: Optimization happens at lower layers transparently

TIMING: ~2.5 minutes

Q2: WHAT IS THE ROLE OF WORKERS IN PLAYWRIGHT?
================================================================================

INTERVIEWER: "What are workers and why does Playwright use them?"

ANSWER STRUCTURE:

1. DEFINE IT
────────────
"Workers are independent Node.js processes that run tests in parallel. 
Playwright creates multiple workers to execute tests concurrently, 
significantly reducing total test execution time."

2. KEY COMPONENTS
──────────────────
• Main Process: Discovers tests, distributes to workers, aggregates results
• Worker Processes: Run actual tests with isolated browsers
• Test Queue: FIFO queue of tests waiting assignment
• Distribution Algorithm: Assigns tests to available workers

3. HOW IT WORKS
────────────────
6 workers on 6-core system + 17 tests:

Worker 1: Test 1 → Test 7 → Test 13
Worker 2: Test 2 → Test 8 → Test 14
Worker 3: Test 3 → Test 9 → Test 15
Worker 4: Test 4 → Test 10 → Test 16
Worker 5: Test 5 → Test 11 → Test 17
Worker 6: Test 6 → Test 12

Each worker finishes its test, picks next from queue.

4. WHY IT MATTERS
──────────────────
✓ Speed: 17 tests in 3 workers finish in ~33% of sequential time
✓ Resource Efficiency: Uses multiple CPU cores
✓ Isolation: Each worker has own browser instance, no test interference
✓ Scalability: Can configure worker count based on system capacity

TIMING: ~2 minutes

Q3: HOW DOES PLAYWRIGHT COMMUNICATE WITH BROWSERS?
================================================================================

INTERVIEWER: "How does Playwright send commands to the browser and 
receive responses?"

ANSWER STRUCTURE:

1. DEFINE IT
────────────
"Playwright uses Chrome DevTools Protocol (CDP), a JSON-RPC protocol 
over WebSocket, for bidirectional communication with browsers."

2. KEY COMPONENTS
──────────────────
• WebSocket Connection: Persistent connection to browser instance
• CDP Messages: JSON-formatted commands and responses
• Command Executor: Sends instructions to browser
• Event Handler: Receives and processes browser events
• Request-Response Matching: Uses message IDs to correlate requests/responses

3. HOW IT WORKS
────────────────
Request (Main Process → Browser):
{
  "id": 1,
  "method": "Page.navigate",
  "params": {"url": "https://example.com"}
}

Response (Browser → Main Process):
{
  "id": 1,
  "result": {"frameId": "ABC123"}
}

Events (unsolicited, Browser → Main Process):
{
  "method": "Page.loadEventFired",
  "params": {"timestamp": 1234567890}
}

4. WHY IT MATTERS
──────────────────
✓ Real Automation: Playwright isn't controlling UI, it controls the browser
✓ Reliability: Direct protocol access, not fragile UI automation
✓ Performance: Lightweight JSON messages over WebSocket
✓ Multi-browser: Same protocol works with Chromium, Firefox, WebKit

TIMING: ~2.5 minutes

Q4: EXPLAIN THE LOCATOR ENGINE
================================================================================

INTERVIEWER: "How does Playwright's locator engine work? What types 
of selectors does it support?"

ANSWER STRUCTURE:

1. DEFINE IT
────────────
"The Locator Engine is responsible for finding elements on a page. 
It supports multiple selector types: CSS, XPath, text, role, and test ID."

2. KEY COMPONENTS
──────────────────
• Selector Parser: Identifies selector type (CSS vs XPath)
• Query Generator: Creates JavaScript for selector evaluation
• Element Resolver: Executes in browser context
• Caching Layer: Optional caching for repeated queries
• Fallback Handling: Handles missing elements gracefully

3. HOW IT WORKS
────────────────
const link = page.locator('//a[@class="product"]');

1. Locator Engine recognizes: XPath selector
2. Creates JavaScript:
   document.evaluate('//a[@class="product"]', document, null, 
   XPathResult.FIRST_ORDERED_NODE_TYPE, null).singleNodeValue
3. Sends to browser via CDP Runtime.evaluate
4. Browser executes in page context
5. Returns element reference
6. Playwright caches reference
7. Element ready for interaction

4. WHY IT MATTERS
──────────────────
✓ Flexibility: CSS and XPath options for different scenarios
✓ Reliability: Automatic waiting and retries
✓ Performance: Execution in browser context (no round trips)
✓ User-friendly: Text and role selectors for accessibility testing

TIMING: ~2.5 minutes

Q5: WHAT IS TEST ISOLATION AND HOW IS IT ACHIEVED?
================================================================================

INTERVIEWER: "How does Playwright ensure test isolation? Can one test 
affect another?"

ANSWER STRUCTURE:

1. DEFINE IT
────────────
"Test isolation means each test runs independently without affecting 
other tests. Playwright achieves this through separate browser instances 
per worker."

2. KEY COMPONENTS
──────────────────
• Browser Context: Isolated environment with separate storage
• Cookies Isolation: Each context has own cookies
• Local Storage Isolation: Each context has own storage
• Session Isolation: Different session per context
• Cookies Clearing: Automatic cleanup between tests

3. HOW IT WORKS
────────────────
Worker 1                           Worker 2
├─ Browser instance 1              ├─ Browser instance 2
├─ Context 1                       ├─ Context 1
│  ├─ Cookies: {}                  │  ├─ Cookies: {}
│  ├─ Storage: {}                  │  ├─ Storage: {}
│  └─ DOM: unique                  │  └─ DOM: unique
└─ Test runs in isolation          └─ Test runs independently

Each worker has own browser = no shared state

4. WHY IT MATTERS
──────────────────
✓ Reliability: Tests don't fail due to side effects
✓ Repeatability: Same test produces same result always
✓ Parallelization: Can safely run tests in parallel
✓ Debugging: Issues are contained to single test

TIMING: ~2 minutes

Q6: HOW DOES PLAYWRIGHT HANDLE ASYNCHRONOUS OPERATIONS?
================================================================================

INTERVIEWER: "Playwright API is async/await. How does it handle 
asynchronous communication with the browser?"

ANSWER STRUCTURE:

1. DEFINE IT
────────────
"All Playwright operations return Promises, enabling async/await syntax. 
Internally, Playwright uses Promise resolution to wait for browser responses."

2. KEY COMPONENTS
──────────────────
• Promise Creation: Each API call returns a Promise
• Callback Registration: Promise handlers registered
• WebSocket Wait: Main process waits for browser response
• Response Matching: Browser response matched to original request
• Promise Resolution: Promise resolves with result

3. HOW IT WORKS
────────────────
const result = await page.goto('https://example.com');

1. page.goto() is called
2. Returns Promise immediately (not resolved yet)
3. Sends CDP message to browser
4. Assigns ID to message for tracking
5. Main thread waits on Promise
6. Browser receives, navigates, sends response
7. Response matched to message ID
8. Promise resolves with result
9. await completes, next line executes

4. WHY IT MATTERS
──────────────────
✓ Readability: async/await is cleaner than callbacks
✓ Error Handling: try/catch works naturally
✓ Performance: Other tests continue while waiting
✓ Maintainability: Sequential code looks synchronous

TIMING: ~2 minutes

Q7: WHAT IS THE DATA FLOW IN A TEST?
================================================================================

INTERVIEWER: "Walk me through what happens from test start to finish"

ANSWER STRUCTURE:

1. DEFINE IT
────────────
"Data flow is the journey of a test command through the architecture, 
from user code → API → protocol → browser → website → back to user."

2. KEY COMPONENTS
──────────────────
• Input: Test command (e.g., page.click)
• Processing: Locator resolution, validation
• Transmission: CDP message serialization
• Execution: Browser performs action
• Response: Result sent back
• Output: Promise resolved, user code continues

3. HOW IT WORKS
────────────────
Example: await page.click('#button');

Input:  page.click('#button')
  ↓
API Layer:  Recognize as click action on CSS selector
  ↓
Locator:    Resolve '#button' to DOM element
  ↓
Protocol:   Create CDP Input.dispatchMouseEvent command
  ↓
Serialize:  Convert to JSON, add message ID
  ↓
Transmit:   Send over WebSocket to browser
  ↓
Browser:    Parse CDP, route to Input handler
  ↓
Execute:    Simulate mouse click at element coordinates
  ↓
Response:   Send success result back
  ↓
Parse:      Match response to message ID
  ↓
Resolve:    Promise resolves
  ↓
Output:     Next line in test executes

4. WHY IT MATTERS
──────────────────
✓ Understanding: Know what's happening behind the scenes
✓ Debugging: Can trace issues to specific layer
✓ Performance: Understand where bottlenecks occur
✓ Troubleshooting: Better error interpretation

TIMING: ~3 minutes

Q8: EXPLAIN COMMUNICATION PATTERNS
================================================================================

INTERVIEWER: "What communication patterns does Playwright use to talk 
to the browser?"

ANSWER STRUCTURE:

1. DEFINE IT
────────────
"Playwright uses three main communication patterns: request-response 
(synchronous wait), fire-and-forget (async callbacks), and event streaming."

2. KEY COMPONENTS
──────────────────
PATTERN 1 - REQUEST-RESPONSE
  └─ Send command, wait for response
     Example: await page.goto() blocks until page loads

PATTERN 2 - FIRE-AND-FORGET
  └─ Register listener, continue immediately
     Example: page.on('popup', handler) doesn't block

PATTERN 3 - EVENT STREAMING
  └─ Continuous events without request
     Example: page.on('framenavigated') fires repeatedly

3. HOW IT WORKS
────────────────
REQUEST-RESPONSE:
  Send → [Wait] → Receive → Resolve
  
FIRE-AND-FORGET:
  Register → Continue immediately → [Events arrive later] → Handle

EVENT-STREAMING:
  Register → [Continuous events] → Handle each event

4. WHY IT MATTERS
──────────────────
✓ Flexibility: Choose pattern for each scenario
✓ Performance: Don't block on fire-and-forget operations
✓ Responsiveness: Can react to browser events
✓ Control: Fine-grained communication control

TIMING: ~2 minutes

Q9: HOW DOES PLAYWRIGHT OPTIMIZE PERFORMANCE?
================================================================================

INTERVIEWER: "How does Playwright architecture optimize for performance?"

ANSWER STRUCTURE:

1. DEFINE IT
────────────
"Playwright optimizes through parallelization, resource isolation, 
batching operations, and headless browser mode."

2. KEY COMPONENTS
──────────────────
• Parallelization: Multiple workers execute tests simultaneously
• Resource Isolation: Each worker has own browser, no contention
• Batching: Multiple operations sent in single round trip
• Headless Mode: No GUI overhead, faster execution
• Caching: Element references cached when appropriate
• Protocol Efficiency: JSON-RPC minimal overhead

3. HOW IT WORKS
────────────────
Without optimization:
  17 tests sequential = 17 × 1 minute = 17 minutes

With 6 workers:
  17 tests parallel = 17 ÷ 6 ≈ 3 minutes (5.7x speedup)

Batching optimization:
  3 clicks sequential = 3 round trips × 200ms = 600ms
  3 clicks batched = 1 round trip × 200ms = 200ms (3x faster)

4. WHY IT MATTERS
──────────────────
✓ Speed: Tests finish faster, faster feedback to developers
✓ Cost: Reduced CI/CD time saves money
✓ Scalability: Can handle large test suites efficiently
✓ Developer Experience: Quick feedback loop

TIMING: ~2.5 minutes

Q10: WHAT HAPPENS IF A WORKER CRASHES?
================================================================================

INTERVIEWER: "What's the error handling strategy if a worker process fails?"

ANSWER STRUCTURE:

1. DEFINE IT
────────────
"If a worker crashes, the test runner detects the failure, marks the 
test as failed, and reassigns remaining tests to other workers."

2. KEY COMPONENTS
──────────────────
• Process Monitoring: Main process watches worker processes
• Health Checks: Periodically verify worker responsiveness
• Crash Detection: Detects when worker exits unexpectedly
• State Recovery: No recovery attempted; test marked failed
• Test Reassignment: Remaining tests reassigned to healthy workers
• Error Reporting: Full context recorded (logs, screenshots)

3. HOW IT WORKS
────────────────
Worker 1 crashes:
  ├─ Main process detects worker death
  ├─ Current test marked: FAILED (worker crash)
  ├─ Remaining queued tests reassigned to other workers
  ├─ Continue execution with remaining 5 workers
  └─ Report includes worker death details

4. WHY IT MATTERS
──────────────────
✓ Reliability: One worker crash doesn't stop all tests
✓ Debugging: Know which test caused crash
✓ Resilience: Can continue testing with reduced capacity
✓ Observability: Full error context captured

TIMING: ~2 minutes

Q11: COMPARE PLAYWRIGHT vs SELENIUM ARCHITECTURE
================================================================================

INTERVIEWER: "How is Playwright's architecture different from Selenium?"

ANSWER STRUCTURE:

1. DEFINE IT
────────────
"Playwright and Selenium differ fundamentally in how they communicate 
with browsers and manage resources."

2. KEY COMPONENTS - PLAYWRIGHT
──────────────────────────────
✓ CDP Protocol: Direct browser protocol
✓ Single Process: Tests share session
✓ Async/Await: Native promise-based
✓ Multi-browser: Same code for all browsers
✓ Auto-waiting: Built-in element waiting

2b. KEY COMPONENTS - SELENIUM
──────────────────────────────
✗ WebDriver Protocol: Standard but less direct
✗ Server Architecture: Separate server process
✗ Callback-based: Old-style async handling
✗ Browser-specific: Different implementations
✗ Manual waiting: Explicit waits needed

3. HOW IT WORKS - PLAYWRIGHT
──────────────────────────────
Test → Playwright Client → WebSocket → CDP → Browser

Direct, single connection per page

3b. HOW IT WORKS - SELENIUM
──────────────────────────────
Test → Selenium WebDriver Client → HTTP → Selenium Server → WebDriver → Browser

Multi-hop communication, server overhead

4. WHY IT MATTERS
──────────────────
✓ Speed: Direct CDP faster than HTTP server hops
✓ Reliability: Fewer layers = fewer failure points
✓ Features: CDP provides more capabilities
✓ Modern: Built for async/await era

TIMING: ~2.5 minutes

Q12: HOW DOES PLAYWRIGHT HANDLE FIXTURE DEPENDENCIES?
================================================================================

INTERVIEWER: "How does the fixture system work and resolve dependencies?"

ANSWER STRUCTURE:

1. DEFINE IT
────────────
"Fixtures are reusable test setup/teardown. The fixture system manages 
dependencies and ensures proper initialization and cleanup order."

2. KEY COMPONENTS
──────────────────
• Fixture Declaration: Define with test.extend()
• Dependency Graph: System maps fixture dependencies
• Initialization Order: Topological sort of dependencies
• Scope: test, worker, or project scope
• Cleanup: Automatic teardown in reverse order

3. HOW IT WORKS
────────────────
test.extend({
  testUser: async ({}, use) => {
    const user = await createUser();     // Setup
    await use(user);                     // Pass to test
    await deleteUser(user.id);           // Cleanup
  },
  testProduct: async ({testUser}, use) => {  // Depends on testUser
    const product = await createProduct(testUser);
    await use(product);
    await deleteProduct(product.id);
  }
});

Execution order:
  1. testUser setup (createUser)
  2. testProduct setup (createProduct) - testUser available
  3. Test runs with both fixtures
  4. testProduct cleanup (deleteProduct)
  5. testUser cleanup (deleteUser)

Reverse cleanup order ensures dependencies still valid

4. WHY IT MATTERS
──────────────────
✓ Reusability: Fixtures shared across tests
✓ Safety: Proper setup/teardown order guaranteed
✓ Isolation: Each test gets fresh fixtures
✓ Maintainability: Clear dependency management

TIMING: ~2.5 minutes

BONUS: DIFFICULT QUESTIONS
================================================================================

Q: "How does Playwright handle infinite loops in browser scripts?"
A: "Browser command timeout (30s default) kills the command. If script 
   infinite loops, that test times out. Worker remains alive, picks 
   next test. Crashed scripts don't crash the worker."

Q: "Can tests interfere through shared browser instance?"
A: "No. Each worker has isolated browser instance. Even within same 
   worker, tests use separate contexts with cleared cookies/storage. 
   Complete isolation guaranteed."

Q: "What's the memory overhead of 6 workers?"
A: "~450MB per browser instance + ~100MB per worker = ~3.3GB total for 
   6 workers. Trade: memory for speed. Can configure workers based on 
   available resources."

Q: "How does headless mode differ architecturally?"
A: "Headless disables GUI rendering pipeline (GTK/Cocoa). No UI updates 
   sent to display. Faster execution. Everything else identical - same 
   DOM, same JavaScript, same CDP protocol."

Q: "What happens with network requests during test?"
A: "Playwright intercepts via CDP Network domain. Can abort, modify, 
   mock requests. No real network calls if intercepted. Reduces test 
   execution time, improves reliability."

INTERVIEW TIPS
================================================================================

DO:
✓ Use the answer structure (Define → Components → Flow → Why)
✓ Give examples when possible
✓ Draw diagrams if allowed
✓ Mention trade-offs (speed vs memory, etc.)
✓ Connect to real problems (why workers help with 1000 tests)

DON'T:
✗ Give overly technical answers about internals you don't need
✗ Forget to explain WHY something matters
✗ Provide answers longer than 3 minutes
✗ Make up details you don't know
✗ Ramble without structure

IF STUCK:
• Admit "I'm not 100% sure about X, but here's what I know..."
• Ask clarifying questions: "Are you interested in performance or reliability?"
• Relate to known frameworks: "Similar to how Selenium works, but..."
• Offer to look it up: "Let me verify the exact message format"

PRACTICE SCENARIOS
================================================================================

SCENARIO 1: "We have 5000 tests taking 3 hours to run. How would you 
             optimize using Playwright architecture?"

ANSWER: "I'd:
  1. Increase workers from default to optimal (CPU cores / 0.8)
  2. Batch independent operations with Promise.all()
  3. Analyze slow tests with traces, see where time goes
  4. Parallelize at test discovery level (split across machines)
  5. Use headless mode (already default)
  6. Network optimization: mock external APIs
  7. Profile browser instances: find memory leaks"


SCENARIO 2: "Tests pass locally but fail randomly in CI. What's your 
             debugging approach using architecture knowledge?"

ANSWER: "First check:
  1. CI runs same worker config as local? (might have fewer cores)
  2. Tests interfering? (verify context isolation works)
  3. Timing issues? (trace shows real timing, not local speed)
  4. Network differences? (CI blocks external, local doesn't)
  5. Worker crash during test? (monitor worker health)
  6. Environment differences? (baseURL, auth tokens)
  7. Race conditions? (typical in parallel execution)"


SCENARIO 3: "A single test takes 2 minutes, much slower than others. 
             How would you diagnose?"

ANSWER: "Using architecture knowledge:
  1. Is it the test code? (async operations, waits)
  2. Is it browser communication? (many CDP messages)
  3. Is it element location? (complex XPath evaluation)
  4. Is it waiting? (wait for element with wrong timeout)
  5. Is it network? (real HTTP calls taking time)
  6. Is it browser? (page loads slowly)
  7. Use tracing: pw.trace shows exact timing per layer"
