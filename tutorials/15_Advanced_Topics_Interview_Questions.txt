1. VISUAL REGRESSION TESTING - INTERVIEW QUESTIONS
====================================================

BEGINNER LEVEL (5 questions)
-----------------------------

Q1: What is visual regression testing and why is it important?

Answer:
Visual regression testing detects unexpected visual changes in the UI by comparing
screenshots across test runs.

Importance:
• Catches CSS regressions automatically
• Ensures pixel-perfect designs
• Validates cross-browser rendering
• Detects layout breaks
• Prevents visual bugs from reaching production

How it works:
1. Baseline: First run captures reference screenshots
2. Comparison: Subsequent runs compare against baseline
3. Detection: Highlights pixel differences
4. Validation: Update baseline when changes are intentional

Real-world example:
A button's color changes from blue to red due to a CSS update. Visual regression
testing automatically detects this change and flags it for review.

---

Q2: How do you create a basic visual regression test in Playwright?

Answer:
Use `toHaveScreenshot()` assertion:

```javascript
import { test, expect } from '@playwright/test';

test('homepage visual test', async ({ page }) => {
  await page.goto('/');
  await expect(page).toHaveScreenshot('homepage.png');
});
```

First run:
• Creates baseline: tests/__screenshots__/test-spec-ts/homepage-chromium.png

Subsequent runs:
• Compares against baseline
• Fails if differences detected
• Creates diff image showing changes

Update baseline when intentional:
```bash
npx playwright test --update-snapshots
```

Q3: What is the difference between full page and element screenshots?

Answer:

Full Page Screenshot:
• Captures entire scrollable page
• Includes content below the fold
• Best for: Complete page validation

```javascript
await expect(page).toHaveScreenshot('full-page.png', {
  fullPage: true
});
```

Element Screenshot:
• Captures specific component
• Focused testing
• Best for: Component validation, faster comparison

```javascript
await expect(page.locator('.header')).toHaveScreenshot('header.png');
```

Comparison:
| Aspect | Full Page | Element |
|--------|-----------|---------|
| Scope | Entire page | Specific component |
| Speed | Slower | Faster |
| Size | Larger file | Smaller file |
| Use case | Layout validation | Component testing |

Q4: How do you handle dynamic content in visual regression tests?

Answer:
Use the `mask` option to hide elements that change:

```javascript
await expect(page).toHaveScreenshot('homepage.png', {
  mask: [
    page.locator('.timestamp'),    // Hides timestamps
    page.locator('.ad-banner'),    // Hides ads
    page.locator('.random-quote'), // Hides random content
    page.locator('.live-counter'), // Hides counters
  ]
});
```

Masked elements appear as pink boxes in screenshots.

Common elements to mask:
• Timestamps and dates
• Advertisement banners
• Random content (quotes, tips)
• Live metrics and counters
• User-specific data
• Loading spinners
• Animated elements

✅ New features
❌ Don't update to make failing tests pass without review!

Q6: How do you configure screenshot comparison threshold and tolerance?

Answer:
Use screenshot options to control sensitivity:

```javascript
await expect(page).toHaveScreenshot('homepage.png', {
  maxDiffPixels: 100,       // Allow 100 pixels to be different
  maxDiffPixelRatio: 0.2,   // Allow 20% of pixels to differ
  threshold: 0.2,           // Per-pixel difference threshold (0-1)
});
```

Option Explanations:

1. **maxDiffPixels**: 
   • Absolute number of pixels allowed to be different
   • Example: maxDiffPixels: 100 allows up to 100 pixels to differ
   • Use when: Small, predictable differences expected

2. **maxDiffPixelRatio**:
   • Percentage of total pixels allowed to differ (0-1)
   • Example: maxDiffPixelRatio: 0.1 = 10% of pixels can differ
   • Use when: Differences proportional to image size

3. **threshold**:
   • How different each individual pixel can be (0-1)
   • 0 = exact match, 1 = any color accepted
   • Example: threshold: 0.2 allows slight color variations
   • Use when: Anti-aliasing or compression causes small color shifts

Recommended Settings:
```javascript
// Strict (exact match)
{ maxDiffPixelRatio: 0.01, threshold: 0.1 }

// Balanced (default)
{ maxDiffPixelRatio: 0.1, threshold: 0.2 }

// Lenient (allow more differences)
{ maxDiffPixelRatio: 0.3, threshold: 0.4 }
```

Q7: How do you handle animations in visual regression testing?

Answer:

Disable Animations (Recommended):

```javascript
await expect(page).toHaveScreenshot('static.png', {
  animations: 'disabled'  // Pauses all animations
});
```

Global Configuration:

```javascript
// playwright.config.ts
export default defineConfig({
  use: {
    screenshot: {
      animations: 'disabled',
    }
  }
});
```

What Gets Disabled:
✓ CSS animations
✓ CSS transitions
✓ Animated GIFs (paused at first frame)
✓ Videos (paused)

Why Disable Animations:
• Consistent screenshots
• No timing issues
• Prevents flaky tests
• Faster test execution

Alternative: Wait for animation to complete

```javascript
// Wait for specific animation
await page.waitForTimeout(1000); // Not recommended

// Better: Wait for CSS to stabilize
await page.waitForSelector('.element', { state: 'attached' });
await page.locator('.element').waitFor({ state: 'visible' });
```

✓ Accept minor rendering differences
✓ Focus on major layout issues
✓ Maintain separate baselines per browser

Q9: How do you test responsive design with visual regression?

Answer:

Multiple Viewport Test:

```javascript
test.describe('Responsive Design', () => {
  const viewports = [
    { width: 1920, height: 1080, name: 'desktop' },
    { width: 768, height: 1024, name: 'tablet' },
    { width: 375, height: 667, name: 'mobile' },
  ];
  
  for (const viewport of viewports) {
    test(`${viewport.name} view`, async ({ page }) => {
      await page.setViewportSize({ 
        width: viewport.width, 
        height: viewport.height 
      });
      
      await page.goto('/');
      
      await expect(page).toHaveScreenshot(`homepage-${viewport.name}.png`);
    });
  }
});
```

Device Emulation:

```javascript
import { devices } from '@playwright/test';

test.use(devices['iPhone 13']);

test('mobile screenshot', async ({ page }) => {
  await page.goto('/');
  await expect(page).toHaveScreenshot('mobile.png');
});
```

Dynamic Viewport Change:

```javascript
test('responsive breakpoints', async ({ page }) => {
  await page.goto('/');
  
  // Desktop
  await page.setViewportSize({ width: 1920, height: 1080 });
  await expect(page).toHaveScreenshot('desktop.png');
  
  // Tablet
  await page.setViewportSize({ width: 768, height: 1024 });
  await expect(page).toHaveScreenshot('tablet.png');
  
  // Mobile
  await page.setViewportSize({ width: 375, height: 667 });
  await expect(page).toHaveScreenshot('mobile.png');
});
```

Common Breakpoints:
• Mobile: 375×667 (iPhone SE)
• Mobile Large: 414×896 (iPhone 11 Pro Max)
• Tablet: 768×1024 (iPad)
• Tablet Landscape: 1024×768
• Desktop: 1366×768
• Desktop Large: 1920×1080

Q10: How do you organize and maintain visual regression test baselines?

Answer:

Directory Structure:

```
tests/
├── visual/
│   ├── homepage.spec.ts
│   ├── products.spec.ts
│   ├── checkout.spec.ts
│   └── components.spec.ts
└── __screenshots__/
    └── visual/
        ├── homepage-spec-ts/
        │   ├── homepage-chromium.png
        │   ├── homepage-firefox.png
        │   └── homepage-webkit.png
        ├── products-spec-ts/
        │   └── product-list-chromium.png
        └── checkout-spec-ts/
            └── payment-step-chromium.png
```

Version Control:

```bash
# Add baselines to Git
git add tests/__screenshots__/
git commit -m "Add visual regression baselines"

# Update baselines
npx playwright test --update-snapshots
git add tests/__screenshots__/
git commit -m "Update visual baselines for design changes"
```

Naming Conventions:

```javascript
// ✅ Good: Descriptive names
await expect(page).toHaveScreenshot('homepage-hero-section.png');
await expect(page).toHaveScreenshot('checkout-payment-step.png');
await expect(page).toHaveScreenshot('dashboard-graphs-dark-mode.png');

// ❌ Bad: Generic names
await expect(page).toHaveScreenshot('test1.png');
await expect(page).toHaveScreenshot('screenshot.png');
```

Maintenance Best Practices:

1. **Review Changes Before Updating:**
```bash
# Run tests to see failures
npx playwright test

# View HTML report
npx playwright show-report

# Review diff images
# Only then update
npx playwright test --update-snapshots
```

2. **Keep Baselines in Git:**
   ✓ Ensures consistency across team
   ✓ Tracks visual changes over time
   ✓ Easy rollback if needed

3. **Clean Up Old Baselines:**
```bash
# Remove unused screenshots
find tests/__screenshots__ -type f -mtime +30 -delete
```

4. **Document Intentional Changes:**
```bash
git commit -m "Update baselines: New brand colors (JIRA-123)"
```

Q11: How do you implement visual regression testing in a CI/CD pipeline?

Answer:

GitHub Actions Workflow:

```yaml
name: Visual Regression Tests
on: [push, pull_request]

jobs:
  visual-tests:
    runs-on: ubuntu-latest
    
    steps:
      - uses: actions/checkout@v3
      
      - uses: actions/setup-node@v3
        with:
          node-version: 18
      
      - name: Install dependencies
        run: npm ci
      
      - name: Install Playwright browsers
        run: npx playwright install --with-deps
      
      - name: Run visual tests
        run: npx playwright test tests/visual/
      
      - name: Upload failure artifacts
        if: failure()
        uses: actions/upload-artifact@v3
        with:
          name: visual-test-results
          path: |
            test-results/
            playwright-report/
          retention-days: 30
```

Docker for Consistency:

```dockerfile
FROM mcr.microsoft.com/playwright:latest

WORKDIR /app
COPY . .

RUN npm ci
RUN npx playwright install --with-deps

CMD ["npx", "playwright", "test"]
```

Why Docker:
✓ Consistent fonts across environments
✓ Same browser versions
✓ Identical rendering
✓ Reproducible results

Baseline Update Workflow:

```yaml
name: Update Visual Baselines
on: workflow_dispatch  # Manual trigger

jobs:
  update-baselines:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - uses: actions/setup-node@v3
      - run: npm ci
      - run: npx playwright install --with-deps
      - run: npx playwright test --update-snapshots
      
      - name: Commit updated baselines
        run: |
          git config user.name "GitHub Actions"
          git config user.email "actions@github.com"
          git add tests/__screenshots__/
          git commit -m "chore: update visual baselines [skip ci]" || echo "No changes"
          git push
```

Best Practices:
• Use same OS in CI as local (Ubuntu recommended)
• Pin browser versions
• Upload diff images as artifacts
• Manual approval for baseline updates
• Review changes in PR

Q12: How do you handle flaky visual regression tests?

Answer:

Common Causes of Flakiness:

1. **Animations Not Disabled:**
```javascript
// ✅ Fix: Disable animations
await expect(page).toHaveScreenshot('page.png', {
  animations: 'disabled'
});
```

2. **Fonts Not Loaded:**
```javascript
// ✅ Fix: Wait for fonts
await page.evaluate(() => document.fonts.ready);
await expect(page).toHaveScreenshot('page.png');
```

3. **Dynamic Timestamps:**
```javascript
// ✅ Fix: Mask dynamic content
await expect(page).toHaveScreenshot('page.png', {
  mask: [page.locator('.timestamp')]
});
```

4. **Network-Dependent Content:**
```javascript
// ✅ Fix: Mock API responses
await page.route('**/api/random-content', route => {
  route.fulfill({
    body: JSON.stringify({ content: 'Fixed content' })
  });
});
await page.goto('/');
await expect(page).toHaveScreenshot('page.png');
```

5. **Incomplete Page Load:**
```javascript
// ✅ Fix: Wait for network idle
await page.goto('/');
await page.waitForLoadState('networkidle');
await expect(page).toHaveScreenshot('page.png');
```

6. **Browser Rendering Differences:**
```javascript
// ✅ Fix: Use appropriate thresholds
await expect(page).toHaveScreenshot('page.png', {
  maxDiffPixelRatio: 0.05,  // Allow 5% difference
  threshold: 0.2             // Allow slight color variations
});
```

7. **Race Conditions:**
```javascript
// ✅ Fix: Wait for specific element
await page.waitForSelector('.loaded-indicator');
await expect(page).toHaveScreenshot('page.png');
```

Debug Flaky Tests:

```javascript
test('debug flaky screenshot', async ({ page }) => {
  await page.goto('/');
  
  // Take multiple screenshots to compare
  for (let i = 0; i < 5; i++) {
    await expect(page).toHaveScreenshot(`attempt-${i}.png`);
    await page.reload();
  }
});
```

Prevention Checklist:
□ Animations disabled
□ Fonts loaded
□ Dynamic content masked
□ APIs mocked
□ Page fully loaded
□ Appropriate thresholds set
□ Stable selectors used

Q13: Explain the difference between component visual testing and full page visual testing. When would you use each?

Answer:

Component Visual Testing:
```javascript
test('button component', async ({ page }) => {
  await page.goto('/components');
  await expect(page.locator('.btn-primary')).toHaveScreenshot('btn.png');
});
```

Characteristics:
• Focused on specific UI component
• Faster execution
• Smaller screenshot files
• Easier to identify changes
• Reusable across pages

Full Page Visual Testing:
```javascript
test('homepage', async ({ page }) => {
  await page.goto('/');
  await expect(page).toHaveScreenshot('homepage.png', {
    fullPage: true
  });
});
```

Characteristics:
• Captures entire page layout
• Slower execution
• Larger screenshot files
• Comprehensive validation
• Detects layout shifts

When to Use Component Testing:

✓ **Design System Validation:**
```javascript
test.describe('Button Variants', () => {
  test('primary', async ({ page }) => {
    await expect(page.locator('.btn-primary')).toHaveScreenshot('btn-primary.png');
  });
  
  test('secondary', async ({ page }) => {
    await expect(page.locator('.btn-secondary')).toHaveScreenshot('btn-secondary.png');
  });
  
  test('disabled', async ({ page }) => {
    await expect(page.locator('.btn-disabled')).toHaveScreenshot('btn-disabled.png');
  });
});
```

✓ **Reusable Components:**
   • Buttons
   • Form inputs
   • Cards
   • Modals
   • Navigation menus

✓ **Isolated Testing:**
   • No dependency on full page context
   • Test component in multiple states
   • Faster feedback loop

When to Use Full Page Testing:

✓ **Layout Validation:**
```javascript
test('responsive layout', async ({ page }) => {
  await page.goto('/');
  await expect(page).toHaveScreenshot('full-layout.png', {
    fullPage: true
  });
});
```

✓ **Critical User Flows:**
   • Homepage
   • Checkout process
   • Dashboard
   • Landing pages

✓ **Regression Detection:**
   • Catch unexpected layout shifts
   • Validate entire page composition
   • Ensure components work together

Best Practice - Combine Both:

```javascript
test.describe('Product Page', () => {
  // Full page test
  test('full page layout', async ({ page }) => {
    await page.goto('/product/123');
    await expect(page).toHaveScreenshot('product-page.png', {
      fullPage: true
    });
  });
  
  // Component tests
  test('product image gallery', async ({ page }) => {
    await page.goto('/product/123');
    await expect(page.locator('.image-gallery')).toHaveScreenshot('gallery.png');
  });
  
  test('product details card', async ({ page }) => {
    await page.goto('/product/123');
    await expect(page.locator('.product-details')).toHaveScreenshot('details.png');
  });
  
  test('add to cart button', async ({ page }) => {
    await page.goto('/product/123');
    await expect(page.locator('.add-to-cart')).toHaveScreenshot('add-to-cart.png');
  });
});
```

Decision Matrix:
| Aspect | Component | Full Page |
|--------|-----------|-----------|
| Speed | Fast | Slow |
| Scope | Narrow | Wide |
| File Size | Small | Large |
| Maintenance | Easy | Complex |
| Use Case | Reusable UI | Page layouts |
| Detection | Specific | Comprehensive |

Q14: Your visual regression tests are failing in CI but passing locally. How do you debug and fix this issue?

Answer:

**Step 1: Identify the Environment Difference**

Common Causes:
1. Different fonts installed
2. Different browser versions
3. Different OS (Windows vs Linux)
4. Different screen DPI
5. Different timezone/locale

**Step 2: Download CI Artifacts**

GitHub Actions:
```yaml
- name: Upload test results
  if: failure()
  uses: actions/upload-artifact@v3
  with:
    name: playwright-results
    path: |
      test-results/
      playwright-report/
```

Download and compare:
• Actual screenshot (what CI generated)
• Expected screenshot (your baseline)
• Diff screenshot (highlighted differences)

**Step 3: Use Docker Locally**

Run same environment as CI:

```bash
# Build Docker image (same as CI)
docker build -t playwright-tests .

# Run tests in Docker
docker run -it playwright-tests npx playwright test

# Update snapshots in Docker
docker run -it playwright-tests npx playwright test --update-snapshots

# Copy updated snapshots from container
docker cp <container_id>:/app/tests/__screenshots__ ./tests/
```

Dockerfile:
```dockerfile
FROM mcr.microsoft.com/playwright:latest
WORKDIR /app
COPY . .
RUN npm ci
RUN npx playwright install --with-deps
```

**Step 4: Font Consistency**

Install missing fonts in CI:

```yaml
- name: Install fonts
  run: |
    sudo apt-get update
    sudo apt-get install -y fonts-liberation fonts-noto-color-emoji
```

Or use web fonts:
```javascript
// playwright.config.ts
export default defineConfig({
  use: {
    viewport: { width: 1280, height: 720 },
    screenshot: {
      fonts: ['Roboto', 'Arial']  // Ensure fonts are loaded
    }
  }
});
```

**Step 5: Browser Version Consistency**

Pin Playwright version:

```json
// package.json
{
  "dependencies": {
    "@playwright/test": "1.40.0"  // Specific version, not ^1.40.0
  }
}
```

**Step 6: Locale and Timezone**

Set consistent locale:

```javascript
// playwright.config.ts
export default defineConfig({
  use: {
    locale: 'en-US',
    timezoneId: 'America/New_York',
  }
});
```

**Step 7: Generate Baselines in CI**

Update snapshots in CI environment:

```yaml
name: Update Baselines
on: workflow_dispatch

jobs:
  update:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - uses: actions/setup-node@v3
      - run: npm ci
      - run: npx playwright install --with-deps
      - run: npx playwright test --update-snapshots
      
      - name: Create PR
        run: |
          git checkout -b update-screenshots-${{ github.run_id }}
          git add tests/__screenshots__/
          git commit -m "Update screenshots from CI"
          git push origin update-screenshots-${{ github.run_id }}
```

**Step 8: Adjust Thresholds**

If minor differences are acceptable:

```javascript
await expect(page).toHaveScreenshot('page.png', {
  maxDiffPixelRatio: 0.05,  // Allow 5% difference
  threshold: 0.2             // Allow slight color shifts
});
```

**Prevention Checklist:**
□ Use Docker for local and CI
□ Pin Playwright version
□ Generate baselines in CI
□ Install same fonts
□ Set consistent locale
□ Disable animations
□ Use appropriate thresholds

Q15: You need to implement dark mode testing with visual regression. What's your approach?

Answer:

**Implementation Strategy:**

**1. Test Both Themes**

```javascript
test.describe('Theme Testing', () => {
  test.describe('Light Theme', () => {
    test.beforeEach(async ({ page }) => {
      await page.goto('/');
      await page.evaluate(() => {
        localStorage.setItem('theme', 'light');
        document.documentElement.setAttribute('data-theme', 'light');
      });
    });
    
    test('homepage light', async ({ page }) => {
      await page.goto('/');
      await expect(page).toHaveScreenshot('homepage-light.png');
    });
    
    test('dashboard light', async ({ page }) => {
      await page.goto('/dashboard');
      await expect(page).toHaveScreenshot('dashboard-light.png');
    });
  });
  
  test.describe('Dark Theme', () => {
    test.beforeEach(async ({ page }) => {
      await page.goto('/');
      await page.evaluate(() => {
        localStorage.setItem('theme', 'dark');
        document.documentElement.setAttribute('data-theme', 'dark');
      });
    });
    
    test('homepage dark', async ({ page }) => {
      await page.goto('/');
      await expect(page).toHaveScreenshot('homepage-dark.png');
    });
    
    test('dashboard dark', async ({ page }) => {
      await page.goto('/dashboard');
      await expect(page).toHaveScreenshot('dashboard-dark.png');
    });
  });
});
```

**2. Use Custom Fixture for Theme**

```javascript
// fixtures.ts
import { test as base } from '@playwright/test';

type ThemeFixture = {
  theme: (themeName: 'light' | 'dark') => Promise<void>;
};

export const test = base.extend<ThemeFixture>({
  theme: async ({ page }, use) => {
    const setTheme = async (themeName: 'light' | 'dark') => {
      await page.evaluate((theme) => {
        localStorage.setItem('theme', theme);
        document.documentElement.setAttribute('data-theme', theme);
      }, themeName);
      
      // Wait for theme transition
      await page.waitForTimeout(100);
    };
    
    await use(setTheme);
  },
});
```

Usage:
```javascript
import { test, expect } from './fixtures';

test('dark mode homepage', async ({ page, theme }) => {
  await page.goto('/');
  await theme('dark');
  await expect(page).toHaveScreenshot('homepage-dark.png');
});
```

**3. Test Theme Toggle**

```javascript
test('theme switcher', async ({ page }) => {
  await page.goto('/');
  
  // Light mode (default)
  await expect(page).toHaveScreenshot('initial-light.png');
  
  // Toggle to dark
  await page.click('#theme-toggle');
  await page.waitForTimeout(300); // Wait for CSS transition
  await expect(page).toHaveScreenshot('toggled-dark.png');
  
  // Toggle back to light
  await page.click('#theme-toggle');
  await page.waitForTimeout(300);
  await expect(page).toHaveScreenshot('toggled-light.png');
});
```

**4. Test All Components in Both Themes**

```javascript
const themes = ['light', 'dark'];
```

Q16: What is performance testing and why is it important in web applications?

Answer:
Performance testing measures how fast and responsive a web application is under
various conditions.

Key Metrics:
• Page load time
• Time to interactive
• Response times
• Resource loading
• JavaScript execution
• Memory usage

Importance:

1. **User Experience:**
   • 53% of users abandon sites that take >3 seconds to load
   • Faster sites = better UX = higher engagement

2. **Business Impact:**
   • Amazon: 100ms delay = 1% revenue loss
   • Google: 500ms delay = 20% traffic drop
   • Walmart: 1s improvement = 2% conversion increase

3. **SEO:**
   • Google uses page speed as ranking factor
   • Core Web Vitals affect search rankings

4. **Cost:**
   • Slower sites consume more resources
   • Higher bandwidth costs
   • More server capacity needed

Types of Performance Testing:
• Load Time Testing: How fast pages load
• Stress Testing: Behavior under heavy load
• Spike Testing: Sudden traffic increases
• Endurance Testing: Long-term stability
• Scalability Testing: Growth capacity

Q17: How do you measure page load time in Playwright?

Answer:

Using Navigation Timing API:

```javascript
test('measure page load', async ({ page }) => {
  await page.goto('/');
  
  const timing = await page.evaluate(() => {
    const perf = performance.timing;
    return {
      dnsLookup: perf.domainLookupEnd - perf.domainLookupStart,
      tcpConnection: perf.connectEnd - perf.connectStart,
      serverResponse: perf.responseEnd - perf.requestStart,
      domInteractive: perf.domInteractive - perf.navigationStart,
      domComplete: perf.domComplete - perf.navigationStart,
      pageLoad: perf.loadEventEnd - perf.navigationStart,
    };
  });
  
  console.log('Performance Metrics:');
  console.log(`DNS Lookup: ${timing.dnsLookup}ms`);
  console.log(`TCP Connection: ${timing.tcpConnection}ms`);
  console.log(`Server Response: ${timing.serverResponse}ms`);
  console.log(`DOM Interactive: ${timing.domInteractive}ms`);
  console.log(`DOM Complete: ${timing.domComplete}ms`);
  console.log(`Total Page Load: ${timing.pageLoad}ms`);
  
  // Assert performance budget
  expect(timing.pageLoad).toBeLessThan(3000); // 3 seconds max
});
```

Timing Breakdown:

1. **DNS Lookup**: Time to resolve domain name to IP address
2. **TCP Connection**: Time to establish TCP connection
3. **Server Response**: Time for server to process and respond
4. **DOM Interactive**: When DOM is ready (user can start interacting)
5. **DOM Complete**: When all resources (images, CSS, JS) are loaded
6. **Page Load**: Total time from navigation start to load event

Visual Representation:
```

                  ├─ Resource Loading

                  ├─ Load Event
```

Q18: What are Core Web Vitals and how do you measure them in Playwright?

Answer:

Core Web Vitals are Google's metrics for user experience:

1. **LCP (Largest Contentful Paint)**
   • Measures loading performance
   • When largest element becomes visible
   • Good: < 2.5s, Poor: > 4.0s

2. **FID (First Input Delay)**
   • Measures interactivity
   • Time from first interaction to browser response
   • Good: < 100ms, Poor: > 300ms

3. **CLS (Cumulative Layout Shift)**
   • Measures visual stability
   • How much layout shifts during page load
   • Good: < 0.1, Poor: > 0.25

Measuring LCP:

```javascript
test('measure LCP', async ({ page }) => {
  await page.goto('/');
  
  const lcp = await page.evaluate(() => {
    return new Promise(resolve => {
      new PerformanceObserver(list => {
        const entries = list.getEntries();
        const lastEntry = entries[entries.length - 1];
        resolve(lastEntry.renderTime || lastEntry.loadTime);
      }).observe({ entryTypes: ['largest-contentful-paint'] });
      
      // Timeout after 10 seconds
      setTimeout(() => resolve(0), 10000);
    });
  });
  
  console.log(`LCP: ${lcp}ms`);
  expect(lcp).toBeLessThan(2500); // Good: < 2.5s
});
```

Measuring CLS:

```javascript
test('measure CLS', async ({ page }) => {
  await page.goto('/');
  await page.waitForLoadState('networkidle');
  
  const cls = await page.evaluate(() => {
    return new Promise(resolve => {
      let clsScore = 0;
      
      new PerformanceObserver(list => {
        for (const entry of list.getEntries()) {
          if (!entry.hadRecentInput) {
            clsScore += entry.value;
          }
        }
        resolve(clsScore);
      }).observe({ entryTypes: ['layout-shift'] });
      
      setTimeout(() => resolve(clsScore), 5000);
    });
  });
  
  console.log(`CLS: ${cls}`);
  expect(cls).toBeLessThan(0.1); // Good: < 0.1
});
```

Thresholds:

| Metric | Good | Needs Improvement | Poor |
|--------|------|-------------------|------|
| LCP | < 2.5s | 2.5s - 4.0s | > 4.0s |
| FID | < 100ms | 100ms - 300ms | > 300ms |
| CLS | < 0.1 | 0.1 - 0.25 | > 0.25 |

Why They Matter:
✓ Directly impact user experience
✓ Affect Google search rankings
✓ Correlate with conversion rates
✓ Measure actual user experience

Q19: What is a performance budget and how do you enforce it?

Answer:

A performance budget sets limits on performance metrics to prevent regressions.

Define Performance Budget:

```javascript
// performance-budgets.ts
export const budgets = {
  // Timing budgets
  pageLoad: 3000,        // 3 seconds
  domInteractive: 1500,  // 1.5 seconds
  apiResponse: 500,      // 500ms per API call
  
  // Core Web Vitals
  lcp: 2500,             // 2.5 seconds
  fid: 100,              // 100ms
  cls: 0.1,              // 0.1 score
  
  // Resource budgets
  totalSize: 3000000,    // 3MB total page weight
  jsSize: 500000,        // 500KB total JavaScript
  cssSize: 100000,       // 100KB total CSS
  imageSize: 200000,     // 200KB per image
  
  // Request budgets
  requestCount: 50,      // 50 total requests
  apiCallCount: 10,      // 10 API calls max
};
```

Enforce in Tests:

```javascript
import { budgets } from './performance-budgets';

test('performance budgets', async ({ page }) => {
  let totalSize = 0;
  let requestCount = 0;
  let jsSize = 0;
  let cssSize = 0;
  
  page.on('response', async response => {
    requestCount++;
    
    const size = parseInt(response.headers()['content-length'] || '0');
    totalSize += size;
    
    const contentType = response.headers()['content-type'] || '';
    if (contentType.includes('javascript')) {
      jsSize += size;
    } else if (contentType.includes('css')) {
      cssSize += size;
    }
  });
  
  await page.goto('/');
  await page.waitForLoadState('networkidle');
  
  const timing = await page.evaluate(() => {
    const perf = performance.timing;
    return {
      pageLoad: perf.loadEventEnd - perf.navigationStart,
      domInteractive: perf.domInteractive - perf.navigationStart,
    };
  });
  
  // Assert budgets
  expect(timing.pageLoad).toBeLessThan(budgets.pageLoad);
  expect(timing.domInteractive).toBeLessThan(budgets.domInteractive);
  expect(totalSize).toBeLessThan(budgets.totalSize);
  expect(jsSize).toBeLessThan(budgets.jsSize);
  expect(cssSize).toBeLessThan(budgets.cssSize);
  expect(requestCount).toBeLessThan(budgets.requestCount);
  
  console.log('Performance Budget Results:');
  console.log(`Page Load: ${timing.pageLoad}ms / ${budgets.pageLoad}ms`);
  console.log(`Total Size: ${totalSize} bytes / ${budgets.totalSize} bytes`);
  console.log(`Requests: ${requestCount} / ${budgets.requestCount}`);
});
```

Benefits:
✅ Prevents performance regressions
✅ Catches issues early in development
✅ Aligns team on performance goals
✅ Provides objective targets
✅ Fails builds if budgets exceeded

Best Practices:
• Set realistic budgets based on user research
• Different budgets for different pages (homepage vs dashboard)
• Different budgets for different networks (3G vs 4G)
• Review and update budgets regularly
• Fail CI/CD if budgets exceeded

Q20: How do you measure API response time in Playwright?

Answer:

Track API Performance:

```javascript
test('API performance', async ({ page }) => {
  const apiTiming = [];
  
  page.on('response', response => {
    if (response.url().includes('/api/')) {
      const timing = response.timing();
      apiTiming.push({
        url: response.url(),
        method: response.request().method(),
        status: response.status(),
        duration: timing ? timing.responseEnd : 0
      });
    }
  });
  
  await page.goto('/dashboard');
  await page.waitForLoadState('networkidle');
  
  console.log(`Total API calls: ${apiTiming.length}`);
  
  apiTiming.forEach(api => {
    console.log(`${api.method} ${api.url}: ${api.duration}ms (${api.status})`);
  });
  
  // Assert all APIs are fast
  const slowAPIs = apiTiming.filter(api => api.duration > 1000);
  expect(slowAPIs.length).toBe(0);
  
  // Average API response time
  const avgResponseTime = apiTiming.reduce((sum, api) => sum + api.duration, 0) / apiTiming.length;
  console.log(`Average API response time: ${avgResponseTime}ms`);
  expect(avgResponseTime).toBeLessThan(500); // 500ms average
});
```
