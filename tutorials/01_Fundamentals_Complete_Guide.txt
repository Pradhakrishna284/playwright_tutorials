1. WHAT IS PLAYWRIGHT?
================================================================================

Definition
----------
Playwright is an open-source Node.js library developed by Microsoft for end-to-end 
testing of web applications. It allows you to automate browser interactions 
across Chromium, Firefox, and WebKit with a single unified API.

Key Characteristics
-------------------
• Cross-browser: Works with Chromium, Firefox, and WebKit (Safari engine)
• Cross-platform: Runs on Windows, macOS, and Linux
• Modern architecture: Built from the ground up for modern web apps
• Auto-waiting: Eliminates need for manual waits and timeouts
• Full control: Intercept network requests, mock APIs, modify responses

Why Playwright?
---------------
Traditional testing tools (like Selenium) were built 10+ years ago when web 
applications were simpler. Modern web apps are:
• Dynamic (content changes without page reload)
• Asynchronous (multiple requests happening simultaneously)
• Complex (Shadow DOM, iframes, multiple tabs)

Playwright was designed specifically for these challenges.

8 Key Features
--------------

1. AUTO-WAITING MECHANISM
   Automatically waits for elements to be actionable:
   
   await page.click('#submit-button');
   
   Playwright automatically:
   • Waits for button to exist
   • Waits for button to be visible
   • Waits for button to be enabled
   • Waits for button to be stable (not moving)
   • Then clicks

2. CROSS-BROWSER TESTING
   Test same code on Chrome, Firefox, and Safari
   • Consistent API across all browsers
   • No browser-specific code needed
   
   test('login works', async ({ page }) => {
     await page.goto('https://example.com');
     // Works on Chrome, Firefox, and Safari
   });

3. MULTIPLE TABS AND WINDOWS
   • Easy handling of popups
   • Work with multiple browser tabs simultaneously
   • Test complex multi-window scenarios

4. NETWORK INTERCEPTION
   • Mock API responses
   • Block unwanted requests
   • Modify request/response data
   • Test offline scenarios

5. MOBILE EMULATION
   • Test on mobile devices
   • Emulate iPhone, Android, iPad, etc.
   • Test responsive designs
   • Touch events and gestures

6. VISUAL REGRESSION TESTING
   • Screenshot comparison
   • Detect unintended UI changes
   • Pixel-perfect testing

7. MODERN WEB SUPPORT
   • Shadow DOM
   • Web Components
   • iframes
   • SPAs (Single Page Applications)

8. DEBUGGING TOOLS
   • Playwright Inspector (step-by-step debugging)
   • Trace Viewer (timeline of test execution)
   • Codegen (record and generate tests)
   • UI Mode (interactive test running)

Core Architecture
-----------------
Playwright communicates directly with browser DevTools Protocol:
• Faster than HTTP-based protocols (like Selenium)
• More reliable
• Better control over browser

Who Uses Playwright?
--------------------
• Microsoft (creators)
• VS Code, Bing, GitHub
• Many Fortune 500 companies

Comparison: Playwright vs Selenium
-----------------------------------
Playwright                    | Selenium
------------------------------|----------------------------
Modern (2020)                | Legacy (2004)
Auto-waiting built-in        | Manual waits required
Fast                         | Slower
Browser DevTools Protocol    | WebDriver Protocol
Microsoft-backed             | Community-driven
Node.js first                | Java first, Node.js later

Real-World Use Cases
--------------------
1. E-commerce: Test shopping cart, checkout, payment flows
2. Social Media: Test posting, messaging, notifications
3. Banking: Test login, transfers, account management
4. SaaS: Test user registration, subscription, features
5. Mobile Web: Test responsive designs across devices

2. ARCHITECTURE AND SETUP
================================================================================

System Requirements
-------------------
• Node.js: Version 18 or higher (18.x, 20.x, 22.x)
• Operating System: Windows, macOS, or Linux
• Memory: At least 2GB RAM (4GB+ recommended)
• Disk Space: 1GB for Playwright and browsers

Why Node.js?
------------
Playwright is a Node.js library, which means:
1. It runs JavaScript/TypeScript code outside the browser
2. It needs Node.js runtime to execute
3. It uses npm (Node Package Manager) for installation

Installation Methods
--------------------

METHOD 1: Quick Start (Recommended for New Projects)
npm init playwright@latest

This command:
• Creates a new Playwright project
• Prompts for configuration choices
• Generates necessary files and folders

METHOD 2: Manual Installation (Existing Projects)
npm install --save-dev @playwright/test
npx playwright install

Browser Installation
--------------------

Install all browsers:
npx playwright install

Install specific browser:
npx playwright install chromium
npx playwright install firefox
npx playwright install webkit

Install with system dependencies (Linux):
npx playwright install --with-deps

Browser Download Locations:
• Windows: %USERPROFILE%\AppData\Local\ms-playwright
• macOS: ~/Library/Caches/ms-playwright
• Linux: ~/.cache/ms-playwright

  await page.goto('https://playwright.dev/');
  await page.getByRole('link', { name: 'Get started' }).click();
  await expect(page.getByRole('heading', { name: 'Installation' })).toBeVisible();
});

3. NODE.JS AND NPM FUNDAMENTALS
================================================================================

Why Node.js is Required for Playwright
---------------------------------------

Node.js Provides:

1. JAVASCRIPT RUNTIME ENVIRONMENT
   • V8 JavaScript engine (same as Chrome)
   • Executes JavaScript outside the browser
   • Enables running test scripts as standalone applications

2. MODULE SYSTEM
   • CommonJS and ES Modules support
   • Organize code into reusable modules
   • Import/export functionality

3. ASYNCHRONOUS PROGRAMMING
   • Event-driven, non-blocking I/O
   • Perfect for handling async browser operations
   • Native Promise and async/await support

4. PACKAGE MANAGEMENT
   • npm (Node Package Manager) included
   • Install and manage dependencies
   • Version control for packages

5. CROSS-PLATFORM COMPATIBILITY
   • Same code runs on Windows, macOS, Linux
   • Consistent behavior across operating systems

How Node.js Enables JavaScript Execution
-----------------------------------------

Traditional Web (Browser):
HTML → JavaScript Engine (V8) → Web APIs → DOM Manipulation

Node.js (Server/CLI):
JavaScript Code → V8 Engine → Node.js APIs → File System/Network/OS

For Playwright:
Test Script → Node.js (V8) → Playwright Library → Browser Protocols → Browser

Process Flow:
1. You write: test('example', async ({ page }) => { ... })
2. Node.js executes the test function
3. Playwright APIs communicate with browser
4. Browser performs actions
5. Results return to Node.js
6. Assertions verify outcomes

NPM (Node Package Manager)
---------------------------

What npm Does:

1. PACKAGE INSTALLATION
   npm install playwright
   npm install @playwright/test
   npm install --save-dev typescript

2. DEPENDENCY MANAGEMENT
   • Reads package.json
   • Installs all listed dependencies
   • Creates/updates package-lock.json
   • Ensures version consistency

3. SCRIPT EXECUTION
   • Defines scripts in package.json
   • npm test, npm run build

4. VERSION CONTROL
   • Semantic versioning (^1.40.0)
   • Locks exact versions in package-lock.json
   • Prevents "works on my machine" issues

5. BROWSER BINARY MANAGEMENT
   • Playwright uses npm to download browsers
   • Stores in specific cache location
   • Manages multiple versions

NPX (Node Package Executor)
----------------------------

What is npx:
• Comes bundled with npm (since 5.2.0)
• Executes packages without global installation
• Runs local or remote packages

How npx Works:
1. Checks node_modules/.bin/ for package
2. If found, runs local version
3. If not found, downloads temporarily
4. Executes and optionally discards

Benefits:
✓ No global installation pollution
✓ Always uses project-specific version
✓ Try tools without permanent install
✓ Essential for CI/CD consistency

Common npx Commands with Playwright:
npx playwright test              # Run tests
npx playwright test --ui         # UI mode
npx playwright codegen           # Generate tests
npx playwright install           # Install browsers
npx playwright show-report       # View report

package.json vs package-lock.json
----------------------------------

package.json:
• Defines project dependencies
• Specifies version ranges (^, ~)
• Contains project metadata
• Defines npm scripts
• Manually editable

package-lock.json:
• Locks exact versions of all dependencies
• Auto-generated and maintained
• Ensures reproducible installs
• Should be committed to git
• Don't edit manually

Example package.json:
{
  "name": "my-playwright-tests",
  "version": "1.0.0",
  "scripts": {
    "test": "playwright test",
    "test:headed": "playwright test --headed",
    "test:debug": "playwright test --debug"
  },
  "devDependencies": {
    "@playwright/test": "^1.40.0",
    "@types/node": "^20.10.0"
  }
}

5. IMPORT STATEMENT DEEP DIVE
================================================================================

The Essential Import
--------------------
import { test, expect } from '@playwright/test';

Complete Breakdown
------------------

1. 'import' KEYWORD (ES6 Module Syntax)
   • Loads modules at compile time (static imports)
   • Creates immutable bindings
   • Tree-shaking friendly
   • Alternative: Dynamic imports
     const { test } = await import('@playwright/test');

2. DESTRUCTURING SYNTAX { test, expect }
   • Extracts specific named exports
   • More efficient than importing everything
   • Makes dependencies explicit
   • Enables better IDE autocomplete

What You're Actually Importing
-------------------------------

a) test FUNCTION
   Purpose: Define test cases
   
   Variants:
   • test.describe() - Group tests
   • test.beforeEach() - Setup before each test
   • test.afterEach() - Cleanup after each test
   • test.only() - Run only this test
   • test.skip() - Skip this test
   • test.fixme() - Mark as broken
   • test.slow() - Mark as slow test

b) expect FUNCTION
   Purpose: Make assertions
   Auto-waiting: Yes (retries until timeout)
   
   Common Matchers:
   • toHaveText()
   • toBeVisible()
   • toHaveURL()
   • toHaveTitle()
   • toContainText()
   • toHaveCount()
   • toBeEnabled()
   • toBeChecked()

3. 'from @playwright/test'
   • Module specifier
   • @ prefix indicates scoped package
   • @playwright = organization scope
   • /test = specific package within scope

Additional Imports
------------------

Full Import Options:

// Basic imports
import { test, expect } from '@playwright/test';

// Import types (TypeScript)
import { test, expect, Page, Browser, BrowserContext } from '@playwright/test';

// Import devices
import { test, expect, devices } from '@playwright/test';

// Import configuration helpers
import { defineConfig, PlaywrightTestConfig } from '@playwright/test';

Example with Types:
import { test, expect, Page, Locator } from '@playwright/test';

test('typed example', async ({ page }: { page: Page }) => {
  const button: Locator = page.locator('button');
  await button.click();
  await expect(button).toBeDisabled();
});

Import Best Practices
----------------------

1. Only Import What You Need:
   ✓ import { test, expect } from '@playwright/test';
   ✗ import * as playwright from '@playwright/test';

2. Group Related Imports:
   // Playwright imports
   import { test, expect, Page } from '@playwright/test';
   
   // Node.js imports
   import fs from 'fs';
   
   // Custom imports
   import { LoginPage } from './pages/LoginPage';

3. Use Type Imports (TypeScript):
   import type { Page, Locator } from '@playwright/test';
   // Only imports types, removed at runtime

4. Consistent Import Order:
   1. External packages
   2. Playwright imports
   3. Internal modules
   4. Page objects
   5. Fixtures
   6. Utilities

6. TEST FUNCTION ANATOMY
================================================================================

Complete Test Function Structure
---------------------------------
test('descriptive test name', async ({ page }) => {
  // Test implementation
});

Breaking Down Each Part
------------------------

1. test( ... )
   • Function call to Playwright's test runner
   • Registers test with the framework
   • Isolated execution context
   • Auto cleanup after completion

2. 'descriptive test name'
   • First parameter: string
   • Test identifier in reports
   • Should describe what is being tested
   
   Good Names:
   ✓ 'should login with valid credentials'
   ✓ 'displays error for empty email field'
   ✓ 'adds product to cart and updates badge count'
   
   Bad Names:
   ✗ 'test1'
   ✗ 'login'
   ✗ 'works'

3. async
   • Marks function as asynchronous
   • Enables use of await keyword
   • Returns Promise automatically
   • Essential for Playwright's async operations

4. ({ page })
   • Parameter with object destructuring
   • Receives fixtures from Playwright
   • page is most common fixture
   • Can request multiple fixtures

5. => { }
   • Arrow function syntax
   • Function body contains test logic

Available Fixtures
------------------

Built-in Fixtures:

1. page: Page
   • Fresh browser page/tab
   • Most commonly used
   • Auto-created and auto-cleaned

2. context: BrowserContext
   • Browser context (isolated session)
   • Create multiple pages
   • Share cookies/storage across pages

3. browser: Browser
   • Browser instance
   • Create custom contexts
   • Low-level browser control

4. request: APIRequestContext
   • API testing
   • HTTP requests
   • Independent of browser

5. browserName: string
   • 'chromium', 'firefox', or 'webkit'
   • Current browser name
   • Conditional test logic

Complete Test Example
----------------------
import { test, expect } from '@playwright/test';

test.describe('Login Feature', () => {
  
  test.beforeEach(async ({ page }) => {
    await page.goto('/login');
  });
  
  test('should login successfully with valid credentials', async ({ page }) => {
    // Arrange
    const username = 'testuser';
    const password = 'SecurePass123!';
    
    // Act
    await page.fill('#username', username);
    await page.fill('#password', password);
    await page.click('#login-button');
    
    // Assert
    await expect(page).toHaveURL('/dashboard');
    await expect(page.locator('.welcome-message'))
      .toHaveText(`Welcome, ${username}!`);
  });
  
  test.afterEach(async ({ page }) => {
    await page.context().clearCookies();
  });
});

Test Modifiers
--------------

test.only() - Runs only this test
test.skip() - Skips this test
test.fixme() - Marks test as broken
test.slow() - Triples the timeout
test.fail() - Expects test to fail

Example:
test.only('debug this test', async ({ page }) => {
  // Only this runs
});

test.skip('not ready yet', async ({ page }) => {
  // Skipped
});

7. ASYNC/AWAIT MASTERY
================================================================================

Why Asynchronous Programming?
------------------------------

Web Automation is Inherently Async:
1. Network requests take time
2. Pages load progressively
3. Elements render dynamically
4. User interactions have delays
5. API calls are non-instant

The Problem Without Async
--------------------------
Synchronous (Imaginary):
page.goto('https://example.com');  // Starts navigation
page.click('#button');              // Tries immediately - FAILS!
// Button doesn't exist yet because page not loaded

This creates:
• Race conditions
• Flaky tests
• Unreliable results
• "Element not found" errors

The Solution: async/await
--------------------------

async KEYWORD
• Marks function as asynchronous
• Enables await inside function
• Always returns a Promise
• Wraps return value in Promise.resolve()

await KEYWORD
• Pauses execution until Promise resolves
• Unwraps Promise value
• Only works inside async functions
• Makes async code look synchronous

How It Works - Step by Step
----------------------------

Example Test:
test('login flow', async ({ page }) => {
  await page.goto('https://example.com/login');     // Line 1
  await page.fill('#username', 'user');              // Line 2
  await page.fill('#password', 'pass');              // Line 3
  await page.click('#login');                        // Line 4
  await expect(page).toHaveURL('/dashboard');        // Line 5
});

Execution Flow:

Line 1: await page.goto()
• Sends navigation command to browser
• Execution pauses
• Browser loads page
• Promise resolves when page loaded
• Execution continues to Line 2

Line 2: await page.fill('#username', 'user')
• Waits for input to be available
• Waits for input to be visible
• Waits for input to be editable
• Types 'user'
• Execution continues to Line 3

And so on...

Benefits of async/await
-----------------------

1. READABILITY
   Without async/await (Promise chains):
   page.goto('url')
     .then(() => page.fill('#username', 'user'))
     .then(() => page.fill('#password', 'pass'))
     .then(() => page.click('#login'));
   
   With async/await:
   await page.goto('url');
   await page.fill('#username', 'user');
   await page.fill('#password', 'pass');
   await page.click('#login');
   
   Much more readable!

2. ERROR HANDLING
   With async/await:
   try {
     await page.goto('url');
     await page.click('#button');
   } catch (error) {
     console.error(error);
   }

3. DEBUGGING
   • Can set breakpoints normally
   • Step through code line by line
   • Call stack makes sense

Common Patterns
---------------

1. Sequential Operations:
   await page.goto('/login');
   await page.fill('#username', 'user');
   await page.fill('#password', 'pass');
   await page.click('#login');

2. Parallel Operations (when independent):
   const [response1, response2] = await Promise.all([
     page.waitForResponse('**/api/user'),
     page.waitForResponse('**/api/settings')
   ]);

3. Conditional Async:
   const isVisible = await page.locator('#modal').isVisible();
   if (isVisible) {
     await page.click('#close-modal');
   }

4. Loops with Async:
   const items = await page.locator('.item').all();
   for (const item of items) {
     await item.click();
   }

5. Error Handling:
   try {
     await page.goto('https://example.com');
     await page.click('#button');
   } catch (error) {
     console.error('Navigation or click failed:', error);
     throw error;
   }

What Needs await?
-----------------

Requires await:
✓ page.goto()
✓ page.click()
✓ page.fill()
✓ page.waitForSelector()
✓ expect(locator).toBeVisible()
✓ locator.textContent()
✓ locator.count()

Doesn't require await (synchronous):
✗ page.locator()  // Just creates locator
✗ page.url()      // Synchronous getter
✗ test.describe()

Common Mistakes
---------------

1. Forgetting await:
   ❌ Wrong:
   page.goto('url');
   page.click('#button');  // Runs immediately!
   
   ✓ Correct:
   await page.goto('url');
   await page.click('#button');

2. Not handling errors:
   ❌ Silent failure:
   await page.click('#button').catch(() => {});
   
   ✓ Let it fail or handle explicitly:
   try {
     await page.click('#button');
   } catch (error) {
     console.log('Button not found');
     await page.click('#alt-button');
   }

Advanced: Promise.all() for Parallel
-------------------------------------

When operations don't depend on each other:

Sequential (slow - 300ms total):
await page.fill('#field1', 'value1');  // 100ms
await page.fill('#field2', 'value2');  // 100ms
await page.fill('#field3', 'value3');  // 100ms

Parallel (fast - ~100ms total):
await Promise.all([
  page.fill('#field1', 'value1'),
  page.fill('#field2', 'value2'),
  page.fill('#field3', 'value3')
]);

⚠️ Use carefully - operations must be truly independent!

8. BROWSER CONTEXT AND ISOLATION
================================================================================

The Isolation Challenge
------------------------

Scenario: Banking Application Tests

Test 1: Login as User A
Test 2: Transfer funds
Test 3: Logout and login as User B

Problems without isolation:
• Test 2 depends on Test 1's login
• Test 3 sees User A's session
• Tests can't run in parallel
• Random execution order breaks tests
• Flaky, unreliable results

What is a Browser Context?
---------------------------

Definition:
A Browser Context is like an incognito/private browsing session - a completely
isolated browsing environment within a browser instance.

Each Context Has Its Own:
1. Cookies
2. Local Storage
3. Session Storage
4. Cache
5. Permissions (geolocation, notifications, etc.)
6. Authentication state
7. Service Workers

Hierarchy:
Browser
└── Context 1 (isolated)
    ├── Page 1
    ├── Page 2
    └── Page 3
└── Context 2 (isolated)
    ├── Page 1
    └── Page 2

Key Point: Actions in Context 1 don't affect Context 2!

Playwright's Automatic Isolation
---------------------------------

What Playwright Does Per Test:

Before Test Starts:
1. Uses existing browser OR launches new one
2. Creates BRAND NEW browser context
3. Creates fresh page within that context
4. Injects page into test via fixture
5. Test runs with pristine state

After Test Ends:
1. Closes the page
2. Closes and destroys the context
3. All state (cookies, storage) wiped clean
4. Browser may stay open for next test
5. But new context = complete isolation

Visual Example:
Browser Instance (stays open)
│
├── Test 1 Execution
│   └── Context A (created)
│       └── Page (login, do stuff)
│   └── Context A (destroyed) ← All state gone!
│
├── Test 2 Execution
│   └── Context B (brand new)
│       └── Page (fresh start)
│   └── Context B (destroyed)
│
└── Test 3 Execution
    └── Context C (brand new)
        └── Page (no previous state)
    └── Context C (destroyed)

Real-World Example
------------------

test('User A: Successful login', async ({ page }) => {
  // Playwright creates Context 1
  await page.goto('https://bank.example.com/login');
  await page.fill('#username', 'userA');
  await page.fill('#password', 'passA');
  await page.click('#login');
  
  await expect(page).toHaveURL('/dashboard');
  // User A is logged in within THIS context
});
// Playwright destroys Context 1 - User A session GONE!

test('User A: Transfer funds', async ({ page }) => {
  // Playwright creates Context 2 (completely fresh!)
  // NO USER A SESSION! Must login again:
  
  await page.goto('https://bank.example.com/login');
  await page.fill('#username', 'userA');
  await page.fill('#password', 'passA');
  await page.click('#login');
  
  // Now do transfer
  await page.goto('/transfer');
  await page.fill('#amount', '100');
  await page.click('#transfer-button');
  
  await expect(page.locator('.success')).toBeVisible();
});
// Context 2 destroyed

Benefits of Automatic Isolation
--------------------------------

1. TEST INDEPENDENCE
   • Each test starts from known state
   • No dependencies on other tests
   • Tests can run in any order

2. PARALLEL EXECUTION
   • Tests don't interfere with each other
   • Can run simultaneously
   • Faster test completion

3. RELIABILITY
   • No flaky tests from state pollution
   • Predictable, reproducible results
   • If test fails, it's the test or app, not environment

4. EASIER DEBUGGING
   • Isolate exact test that fails
   • No cascade failures
   • Clear cause and effect

5. SIMPLIFIED TEST WRITING
   • No manual cleanup needed
   • Don't worry about previous test state
   • Focus on test logic

Manual Context Management
--------------------------

When You Need Multiple Contexts in One Test:

Example: Testing Multi-User Scenarios

test('chat between two users', async ({ browser }) => {
  // Create two contexts
  const context1 = await browser.newContext();
  const context2 = await browser.newContext();
  
  // Create pages in each context
  const user1Page = await context1.newPage();
  const user2Page = await context2.newPage();
  
  // User 1 logs in
  await user1Page.goto('/login');
  await user1Page.fill('#username', 'user1');
  await user1Page.fill('#password', 'pass1');
  await user1Page.click('#login');
  
  // User 2 logs in (separate session)
  await user2Page.goto('/login');
  await user2Page.fill('#username', 'user2');
  await user2Page.fill('#password', 'pass2');
  await user2Page.click('#login');
  
  // User 1 sends message
  await user1Page.goto('/chat');
  await user1Page.fill('#message', 'Hello!');
  await user1Page.click('#send');
  
  // User 2 receives message
  await user2Page.goto('/chat');
  await expect(user2Page.locator('.message')).toHaveText('Hello!');
  
  // Cleanup
  await context1.close();
  await context2.close();
});

Saving and Reusing Context State
---------------------------------

Save State (e.g., after login):

test.beforeAll(async ({ browser }) => {
  const context = await browser.newContext();
  const page = await context.newPage();
  
  // Login
  await page.goto('/login');
  await page.fill('#username', 'testuser');
  await page.fill('#password', 'password');
  await page.click('#login');
  
  // Save state
  await context.storageState({ path: 'auth.json' });
  await context.close();
});

Reuse State:

test.use({ storageState: 'auth.json' });

test('already logged in', async ({ page }) => {
  // Already authenticated!
  await page.goto('/dashboard');
  await expect(page.locator('.welcome')).toBeVisible();
});

   • Provides actionability checks

Browser → Context → Page Hierarchy
-----------------------------------

```
Browser Instance (Heavy)
├── Context 1 (Lightweight, Isolated)
│   ├── Page 1.1 (Tab/Window)
│   ├── Page 1.2 (Tab/Window)
│   └── Page 1.3 (Tab/Window)
│
├── Context 2 (Lightweight, Isolated)
│   ├── Page 2.1 (Tab/Window)
│   └── Page 2.2 (Tab/Window)
│
└── Context 3 (Lightweight, Isolated)
    └── Page 3.1 (Tab/Window)
```

**Browser:**
• One per worker process
• Heavy resource (spawns actual browser)
• Expensive to create (~seconds)
• Shared across multiple tests (reused)
• Contains browser settings and preferences

**Context:**
• Isolated browsing session (like incognito mode)
• Lightweight (milliseconds to create)
• Own cookies, storage, cache
• Own permissions and geolocation
• Playwright creates new context per test automatically
• Complete isolation between contexts

**Page:**
• Single tab/window within a context
• Represents one web page
• Where you interact with DOM
• Playwright provides one page per test via fixture
• Can create additional pages: context.newPage()

Test Execution Architecture
----------------------------

```
Main Process (Test Runner)
│
├── Worker 1 (Parallel)
│   ├── Browser Instance 1
│   │   └── Context 1 → Page 1 → Test A
│   │   └── Context 2 → Page 2 → Test B
│   │   └── Context 3 → Page 3 → Test C
│
├── Worker 2 (Parallel)
│   ├── Browser Instance 2
│   │   └── Context 1 → Page 1 → Test D
│   │   └── Context 2 → Page 2 → Test E
│
└── Worker 3 (Parallel)
    ├── Browser Instance 3
        └── Context 1 → Page 1 → Test F
        └── Context 2 → Page 2 → Test G
```

How it works:
1. **Main Process** discovers all tests
2. **Workers** are spawned (default: CPU cores / 2)
3. Each **Worker** launches one **Browser** instance
4. Each **Test** gets a fresh **Context** (isolated)
5. Each **Context** has one default **Page**
6. Tests run in **parallel** across workers
7. Contexts are **destroyed** after each test
8. Browser is **reused** for multiple tests within worker


Architecture Summary - Key Takeaways
-------------------------------------

✅ **Three-Layer Architecture:**
   1. Test Code (Your TypeScript/JavaScript)
   2. Playwright Library (Node.js)
   3. Browser (Chromium/Firefox/WebKit)

✅ **Communication:**
   • WebSocket-based protocols
   • Direct browser control
   • No middleware or proxy

✅ **Hierarchy:**
   • Browser (Heavy) → Context (Light) → Page (Single Tab)

✅ **Isolation:**
   • Each test gets fresh context
   • Complete isolation between tests
   • Safe parallel execution

✅ **Workers:**
   • Parallel test execution
   • One browser per worker
   • Multiple tests per browser (different contexts)

✅ **Protocols:**
   • Chromium: Chrome DevTools Protocol
   • Firefox: Juggler (Custom)
   • WebKit: WebKit Protocol (Custom)

✅ **Benefits:**
   • Fast execution (direct protocols)
   • Reliable (built-in waiting)
   • Cross-browser (unified API)
   • Modern (supports latest web features)


Performance Comparison
----------------------

**Selenium WebDriver Architecture:**
Node.js → HTTP → WebDriver Server → JSON → Browser
• Multiple hops, high latency
• HTTP overhead for every command
• JSON serialization/deserialization

**Playwright Architecture:**
Node.js → WebSocket → Binary Protocol → Browser
• Direct connection, low latency
• Efficient binary protocol
• Result: 2-3x faster than Selenium
