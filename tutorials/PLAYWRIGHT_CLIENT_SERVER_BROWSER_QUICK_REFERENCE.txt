================================================================================
PLAYWRIGHT CLIENT-SERVER-BROWSER ARCHITECTURE - QUICK REFERENCE GUIDE
================================================================================

QUICK OVERVIEW
==============

Playwright uses a THREE-TIER CLIENT-SERVER-BROWSER architecture:

TIER 1: CLIENT (Your Test Code)
    └─ What: Your test file (pw_xpath.spec.ts)
    └─ Where: Node.js process on your machine
    └─ Writes: Simple Playwright API calls
    └─ Example: await page.click('#button')

TIER 2: SERVER (Playwright Automation)
    └─ What: Automation server (hidden from you)
    └─ Function: Translates API to CDP commands
    └─ Communicates via WebSocket
    └─ Handles protocol, retries, timeouts

TIER 3: BROWSER (Actual Browser Process)
    └─ What: Chrome.exe, Firefox.exe, etc.
    └─ Where: Separate system process
    └─ Executes: CDP commands
    └─ Returns: Results back to server

EXPLANATION OF MESSAGE FLOW
============================

Step 1: Your Code
    └─ await page.click('#btn')
    └─ Simple Playwright API call

Step 2: Client → Server (WebSocket)
    └─ Send: Click command to selector '#btn'
    └─ Server parses your instruction
    └─ Server converts to Chrome DevTools Protocol

Step 3: Server → Browser (WebSocket)
    └─ Send: {method: "Input.dispatchMouseEvent", params: {...}}
    └─ CDP message sent via WebSocket
    └─ Browser receives the protocol message

Step 4: Browser Execution
    └─ Parse incoming CDP command
    └─ Find element matching selector
    └─ Calculate coordinates
    └─ Simulate mouse click at position
    └─ Trigger click event
    └─ Execute any JavaScript handlers

Step 5: Browser → Server (WebSocket)
    └─ Send: {success: true} response
    └─ Indicates command completed successfully
    └─ Or error details if something failed

Step 6: Server → Your Code
    └─ Response received by server
    └─ JavaScript promise resolves
    └─ await completes
    └─ Next line in test executes

Total Time: Typically 5-50ms for local browser


KEY CONCEPTS
============

1. SEPARATION OF CONCERNS
   ✓ Client: Simple code, no protocol details
   ✓ Server: Protocol, conversion, reliability
   ✓ Browser: Actual execution

2. ABSTRACTION
   ✓ You write: await page.click('#button')
   ✓ Server handles: All the complexity
   ✓ Browser does: The actual work

3. COMMUNICATION METHOD
   ✓ Technology: WebSocket (ws://)
   ✓ Connection: Persistent, bi-directional
   ✓ Format: JSON-RPC messages
   ✓ Port: Dynamic (usually 52xxx)

4. PROTOCOL FLOW
   Client Code → API Call → Server Converts → CDP Message → WebSocket → Browser


WHAT YOU SEE (CLIENT)
=====================

await page.click('#submit-button');
await page.fill('#username', 'john@example.com');
await page.goto('https://example.com');
await expect(page.locator('.success')).toBeVisible();

Simple, readable, one-line commands

Complex protocol messages, handled automatically


WEBSOCKET COMMUNICATION
=======================

Connection: ws://localhost:52613/devtools/browser/xxxxx

Persistent Connection:
    ├─ Established when browser launches
    ├─ Stays open throughout test
    ├─ Allows bi-directional messaging
    └─ Closed when browser closes

Why WebSocket (not HTTP)?
    ✓ Full-duplex communication (both ways)
    ✓ Real-time messaging
    ✓ Browser can send events anytime
    ✓ Lower latency than polling
    ✓ Persistent connection efficiency


MESSAGE TYPES
=============

1. COMMAND (Client → Browser)
   { "id": 42, "method": "Page.navigate", "params": {...} }

2. RESPONSE (Browser → Client)
   { "id": 42, "result": {...} }

3. EVENT (Browser → Client, unsolicited)
   { "method": "Page.frameNavigated", "params": {...} }

4. ERROR (Browser → Client)
   { "id": 42, "error": { "code": -32700, "message": "..." } }


BROWSER SUPPORT
===============

Same CLIENT code, different BROWSER processes:

├─ Chromium: playwright-chromium
├─ Firefox: playwright-firefox
└─ WebKit: playwright-webkit

Server abstracts browser-specific details


BENEFITS OF THIS ARCHITECTURE
==============================

✓ ABSTRACTION
  └─ Users write clean code, complexity hidden

✓ CROSS-BROWSER
  └─ Same code, different browsers

✓ REMOTE EXECUTION
  └─ Browser can run on different machine

✓ SCALABILITY
  └─ Multiple clients/browsers managed

✓ RELIABILITY
  └─ Server handles retries & recovery

✓ MAINTAINABILITY
  └─ Clear separation of concerns

MEMORY & PROCESS SEPARATION
============================

Different Processes = Different Memory Spaces

Client Process (Node.js)
    Memory: Your test code, Playwright API
    PID: e.g., 12345

Browser Process (Chromium/Firefox)
    Memory: Browser engine, DOM, JavaScript
    PID: e.g., 67890

Communication: Only via WebSocket (not direct memory access)


WEBSOCKET PORT ALLOCATION
==========================

Port Assignment:
    ├─ Not fixed (dynamic allocation)
    ├─ Usually in range: 52000-53000
    ├─ Example: ws://localhost:52613/...
    └─ Chosen automatically when browser launches

Why Dynamic?
    ✓ Allows multiple browsers simultaneously
    ✓ Avoids port conflicts
    ✓ Unique for each browser instance


DEBUGGING & INSPECTION
======================

WebSocket Connection URL (in Playwright logs):
    2024-12-29T10:30:45.123Z – Connecting to
    ws://localhost:52613/devtools/browser/xxxxx

Check Active Connections:
    └─ Windows: netstat -ano | find "52613"
    └─ Linux: lsof -i :52613
    └─ Mac: lsof -i :52613

Browser Debug Port:
    └─ Chromium: --remote-debugging-port=9222
    └─ Firefox: No standard debug port


COMMON ISSUES & SOLUTIONS
=========================

1. CONNECTION TIMEOUT
   └─ Browser failed to launch
   └─ Port conflict
   └─ Check browser executable exists

2. WEBSOCKET DISCONNECTED
   └─ Browser crashed
   └─ Network issue
   └─ Check test logs

3. COMMAND TIMEOUT
   └─ Element not found
   └─ Page not loaded
   └─ Wrong selector

4. PROTOCOL ERROR
   └─ Incompatible browser version
   └─ CDP implementation mismatch
   └─ Update Playwright

KEY TAKEAWAYS
=============

1. Three separate tiers: Client, Server, Browser

2. Communication: WebSocket (persistent, bi-directional)

3. Format: JSON-RPC protocol messages

4. Abstraction: Server hides complexity from you

5. You write simple code, server handles protocol

6. Browser executes actual automation commands

7. Results flow back through server to your code

8. Same client code works with different browsers

9. Supports both local and remote execution

10. Persistent connection for entire test session
